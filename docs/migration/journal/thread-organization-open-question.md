# 스레드 상위 조직화 — 열린 설계 질문 (보류)

**Status:** DEFERRED / 관찰 중 (2026-08-15). **의도적으로 구현하지 않는다.**
**Scope:** 저널 Thread 위에 상위 조직화 계층이 필요한가에 대한 미결 설계 질문. 현재 동작을 기술하는 spec 이 아니라, 실사용 증거를 더 모은 뒤 모델링하기 위한 보류 기록이다. (관련 현행 구조: `thread-relation.md`.)

## 배경 — 실사용에서 확실히 발견된 것

`Entry → Thread` 모델은 유효하다. 그런데 실제로 쓰기 시작하니:

1. **Thread 가 예상보다 훨씬 많이 생성된다.** 인간 삶에 동시에 흘렀다 끝나는 작은 서사가 원래 수백 개다(가영님과 불꽃축제 / 궁패스 / 전시, VPUQ-1860 PDF 파싱, LAS 코드 고고학, 모니터 교체, ETF 실험 …). Thread 수가 많은 것은 실패가 아니라 정의를 제대로 잡았다는 신호일 수 있다.
2. **Thread 들 사이에도 반복되는 상위 관계가 보이기 시작한다.** (가영님 관련 3개, 회사-파싱 관련 여러 개 …)

## 열린 질문 — 아직 모르는 것 (이게 더 중요하다)

Thread 위에서 관찰되는 "상위 관계"가 다음 중 무엇인지 **아직 불명확하다.** 하나가 아니라 둘 이상일 수도 있다.

- **분류(Tag)** 로 충분한가? (`가영님`, `회사`, `파싱` 처럼 "무엇에 관한 것인가")
- **상위 서사(Arc)** 인가? (여러 Thread 가 하나의 큰 이야기의 일부: "2026 여름, 가영님과 가까워지던 시기")
- **임의 컬렉션(Collection)** 인가? (서사와 무관하게 "다시 보고 싶은 것들"을 사용자가 골라 담음)
- **단순 목록 탐색 문제** 인가? (끝난 스레드가 앞면을 점령 → 스코프드 홈 + 필터로 해결, 새 개념 0개)

## 개념 후보와 구분선 (지금까지 벼려진 것)

| 개념 | 시제 | 서사성 | 핵심 질문 | 생성 감각 |
|---|---|---|---|---|
| **Thread** | 현재진행 | 있음(한 선의 연속) | 이 순간들을 하나의 전개로 읽을 이유가 있나 | 저절로 자란다(잇는다) |
| **Tag** | — | 없음(술어) | 이것은 무엇에 관한 것인가 | 라벨을 붙인다 |
| **Arc** | 회고 | 있음(여러 선이 한 이야기) | 이것들은 어떤 큰 이야기의 일부인가 | 나중에 발견/선언한다 |
| **Collection** | 회고 | 없음(임의 선별) | 이것들을 왜 같이 보고 싶은가 | 담는다 |

핵심 정의·경고:

- **Thread = duration 이 아니라 narrative continuity.** 3시간짜리도 6개월짜리도 하나의 선이면 Thread. 반대로 1년치 `회사` 기록은 그 안에 독립 사건 수십 개라 보통 하나의 Thread 가 아니다. Thread 를 억지로 키워 개수를 줄이면 "하나의 흐름을 따라간다"는 의미가 희석된다.
- **Arc 는 Thread↔Collection 블러의 재발 위험이 있다.** Arc 도 narrative continuity 라 정의가 Thread 와 같고 스케일만 크다. → Arc 가 별도 명사인지, 아니면 **재귀적(nestable) Thread**(스레드를 원소로 갖는 스레드)인지 미결. 재귀는 명사 1개로 경제적이지만 UI·중첩 깊이 복잡도가 급증하므로 **해답이 아니라 가설**로 둔다.
- **Arc(서사) vs Collection(임의)는 개념적으로 갈리지만 도구로 갈리는지는 불명.** 묶는 그 순간 사용자가 "서사냐 모음이냐"를 신뢰성 있게 판정 못 하면, 둘을 각각 기능으로 만드는 건 관리노동을 재생산한다. → **"스레드를 묶는 도구"는 최대 하나.**
- **Collection 은 개인 저널에서 유독 안 죽는다.** 저자 = 미래의 독자라 큐레이션 수익을 정확히 그 사람이 회수한다. 다만 정당성은 "목록이 길어서"가 아니라 **기록 시점 분류 ≠ 해석 시점 의미**라는 저널 고유의 재해석 층에서 온다.

## 왜 지금 구현하지 않는가

지금 구현하면 머릿속 가설을 데이터 모델로 굳혀버린다. 가장 위험한 실패: `Collection` 을 만들어 놓고 몇 달 뒤 보니 사용 패턴이 사실상 `Tag` 와 같은 경우 — 기능은 늘고 개념은 흐려진다("이름만 다른 태그"). 이는 이 저장소의 수렴 원칙(coexistence 가 아니라 convergence)과도 정면으로 어긋난다. Thread 는 막 실사용되기 시작한 기능이라, 지금의 불편은 귀중한 데이터다. 너무 빨리 해결하면 "사용자가 실제로 어떤 문제를 가졌는가"를 기능으로 덮어버린다.

## 무엇을 관찰하는가 (관찰 장치)

당분간 **Thread 를 아끼지 말고 많이 만든다.** "이것까지 스레드로 만들면 너무 많아지는데?"라는 압박으로 Thread 정의를 크게 잡지 않는다. 3일짜리든 일주일짜리든 하나의 흐름이면 만든다.

그리고 실제 불편 사례를 기록한다(각각 요구사항이 다르다):

- "가영님 관련 스레드 17개를 한눈에 보고 싶었다." → Tag/필터?
- "회사 스레드 40개 중 파싱만 보고 싶었다." → Tag/필터?
- "궁패스·전시·불꽃축제를 하나의 큰 흐름으로 읽고 싶었다." → Arc/재귀 Thread?
- "끝난 스레드 때문에 목록이 지저분해 치우고 싶었다." → archive / 스코프드 홈(lifecycle 축)?
- "특정 스레드 몇 개를 의미와 무관하게 즐겨찾기처럼 모으고 싶었다." → Collection?

**판별 지표(관찰을 생산적으로 만드는 것):** 스레드들을 묶고 싶어질 때마다 자문한다 —

> **순서를 매겨 하나의 시퀀스로 이어읽고 싶은가(→ 서사/Arc, 어쩌면 재귀 Thread), 아니면 그냥 모아서 훑고 싶은가(→ Collection)?**

정렬해서 이어읽고 싶다 = 서사. 모아서 브라우징 = 컬렉션.

**항상 먼저 반증할 null 가설:** "태그 필터 + 최근순으로 이미 해결되지 않나?" 상위 흐름이 *구성(construct)* 대상이 아니라 *필터로 보이는(view)* 것이면 새 명사는 0개이고, 원래 통증(목록 길다)은 스코프드 홈 + 태그 탐색으로 끝난다.

## 언제/어떻게 결정하는가

10~20개의 실제 불편 사례가 쌓이면, 개념을 발명할 필요 없이 사례들을 늘어놓았을 때 **반복되는 구조**가 드러난다. 그때 `Entry → Thread(→ 재귀?) + Tag + (Collection?)` 중 어디로 수렴하는지가 손이 실제로 한 행동으로 답한다. 그 전에는 DB 엔티티를 박지 않는다.
