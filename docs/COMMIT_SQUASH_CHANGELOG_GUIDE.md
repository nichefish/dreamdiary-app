# 커밋 Squash와 CHANGELOG 작성 방법론

이 문서는 작업 중 생성한 세부 커밋을 개념적 마일스톤으로 수렴하고, 그 결과를 릴리스 CHANGELOG로 번역하는 기준을 정의한다.

핵심 흐름은 다음과 같다.

```text
작업 변화 → SAVEPOINT 커밋 → MILESTONE 커밋으로 squash → (증거) → 릴리스 CHANGELOG
```

다만 Squash와 CHANGELOG는 같은 파이프라인에 있어도 **반대 방향의 기록물**이다.

- **Commit / Squash**: 원인을 보존한다. 무엇을 어디서 왜 바꿨는지 복원 가능하게 남긴다.
- **CHANGELOG**: 구현을 버린다. 그 결과 제품에 생긴 의미 있는 차이만 남긴다.

절단선: **Squash 결과는 CHANGELOG의 초안이 아니다. 증거자료일 뿐이다.**
커밋 메시지를 문장만 다듬어 항목화하지 않는다. 반드시 아래 §6의 정보손실(압축) 규칙을 거친다.

## 1. 기록 단위

### SAVEPOINT

SAVEPOINT는 작업 중 안전하게 되돌아가고 검증할 수 있도록 남기는 임시 커밋이다.

- 한 단계의 코드·주석·spec이 서로 일치한다.
- 빌드·테스트·인코딩 게이트와 호출 그래프가 정합하다.
- 구현 순서, 조사 결과, 중간 계측처럼 작업 과정에 가까운 정보를 포함할 수 있다.
- 이후 개념적 경계가 확정되면 다른 SAVEPOINT와 함께 squash할 수 있다.

### MILESTONE

MILESTONE은 하나의 기능, 성능 개선, 구조 수렴 또는 동작 계약이 개념적으로 완결된 영구 커밋이다.

- 커밋 하나만 읽어도 최종 변화의 목적과 결과를 이해할 수 있다.
- 독립적으로 설명하거나 되돌릴 가치가 있는 변화 경계를 가진다.
- 구현 과정이 아니라 최종 코드가 제공하는 현재 동작을 설명한다.
- 릴리스 CHANGELOG의 **증거**가 된다. 초안이 아니다(§6).

SAVEPOINT의 개수와 MILESTONE의 개수는 일치할 필요가 없다. 여러 SAVEPOINT가 하나의 개념을 완성했다면 하나의 MILESTONE으로 압축한다.

## 2. Squash의 목적

Squash는 커밋 수를 줄이는 정리 작업이 아니라, 시간순 작업 기록을 개념적 결과로 수렴시키는 작업이다.

다음 정보는 최종 결과를 이해하는 데 필요하지 않다면 squash 과정에서 제거한다.

- 같은 문제를 해결하기 위한 반복 수정
- 최종 코드에 남지 않은 대안과 시행착오
- 원인 해소 후 제거한 임시 계측
- 오탈자 수정, import 정리, 빌드 복구처럼 앞선 커밋을 완성하기 위한 후속 수정
- 최종 계약과 무관한 작업 순서

다음 정보는 MILESTONE 커밋에 보존한다.

- 변화가 해결한 문제와 최종 결과
- 사용자가 체감하는 기능·성능·안정성 변화
- 이후 개발자가 알아야 할 핵심 데이터·API·캐시·상태 계약
- 재현 가능한 실측 성능 수치와 측정 조건
- 중요한 검증 결과

## 3. Squash 경계 결정

다음 조건을 모두 만족하면 같은 MILESTONE으로 묶을 수 있다.

1. 같은 문제 또는 같은 개념적 목표를 해결한다.
2. 최종 사용자 효과나 구조적 결론을 하나의 문장으로 설명할 수 있다.
3. 함께 되돌리는 것이 자연스럽다.
4. 최종 코드·주석·spec이 하나의 현재 계약으로 수렴한다.

다음 변화는 별도 MILESTONE으로 남긴다.

- 사용자 효과와 책임 영역이 서로 다른 기능
- 독립적으로 되돌릴 가능성이 있는 변경
- 별도의 데이터 마이그레이션이나 운영 절차가 필요한 변경
- 보안, 권한, 데이터 보존처럼 독립 감사 가치가 있는 계약
- 단순히 같은 기간에 작업했다는 이유로만 연결되는 변경

큰 제목 하나로 설명할 수 있더라도 내부 변화가 독립적인 사용자 효과를 가진다면 여러 MILESTONE으로 나눈다. 반대로 구현 파일이나 계층이 여러 개라도 같은 결과를 만들기 위한 변화라면 하나로 묶을 수 있다.

## 4. Squash 절차

### 4.1 경계 확정

먼저 묶을 커밋의 시작점과 끝점을 정하고, 각 SAVEPOINT의 제목과 최종 diff를 함께 확인한다.

```bash
git log --reverse --format="%h %s" <base>..HEAD
git diff --stat <base>..HEAD
```

커밋 메시지는 작업 과정을 파악하는 색인이고, 최종 diff는 실제 결과의 기준이다. 둘이 다르면 최종 코드·spec을 우선하여 MILESTONE 범위를 다시 결정한다.

### 4.2 안전 참조와 트리 기록

히스토리를 변경하기 전에 복구용 참조를 만들고 현재 최종 트리 식별자를 기록한다.

```bash
git branch backup/pre-squash-<milestone>
git rev-parse "HEAD^{tree}"
```

백업 참조는 squash 실패에 대비한 복구 수단이다. 영구 변경 이력이나 CHANGELOG 원천으로 유지하는 것이 목적은 아니다.

### 4.3 개념 단위로 압축

interactive rebase 또는 동등한 Git 절차로 같은 개념의 SAVEPOINT를 하나의 MILESTONE으로 합친다.

```bash
git rebase -i <base>
```

이미 공유된 원격 히스토리를 재작성하는 경우에는 영향 범위와 push 방식을 별도로 확인한다. squash 과정에서 소스 내용을 새로 수정하지 않는다. 내용 변경이 필요하면 rebase를 중단하고 새로운 SAVEPOINT에서 정합성을 먼저 확보한다.

### 4.4 최종 트리 동일성 검증

Squash 전후의 tree object ID가 같아야 한다.

```bash
git rev-parse "HEAD^{tree}"
git diff backup/pre-squash-<milestone> HEAD
```

- tree object ID가 동일해야 한다.
- `git diff` 결과가 없어야 한다.
- 커밋 메시지만 바뀌고 파일 내용은 그대로여야 한다.

검증과 원격 반영이 끝난 뒤에만 백업 참조를 정리한다.

## 5. MILESTONE 커밋 메시지

제목은 Conventional Commits 타입을 유지하고, 한글로 개념적 결과를 표현한다.

```text
perf: 저널 조회·저장 응답 경로 최적화

프론트 자산 전송과 중복 요청을 줄이고 저널 저장의
태그 카테고리 조회를 projection 기반으로 전환한다.

저널 저장 응답은 동일한 개발 환경의 실측 기준으로
약 2.4초에서 0.2초 수준으로 개선된다.
```

메시지는 다음 질문에 답할 수 있어야 한다.

- 무엇이 달라졌는가?
- 왜 하나의 MILESTONE인가?
- 사용자나 운영자가 체감하는 결과는 무엇인가?
- 이후 유지보수자가 지켜야 할 중요한 계약은 무엇인가?

파일 목록, 메서드 이름 나열, SAVEPOINT별 작업 일지는 본문의 중심으로 삼지 않는다. 구현 식별자는 핵심 계약을 정확히 지칭할 때만 사용한다.

## 6. CHANGELOG 작성 — 압축 규율

CHANGELOG는 작업 일지·엔지니어링 로그·ADR 요약이 아니다.
질문은 하나만 쓴다.

> **이 버전으로 올라오면서 제품이 이전 버전과 어떻게 달라졌는가?**

변환 경로:

```text
작업 사실 → 기술적 의미 → 사용자/제품 의미 → CHANGELOG
```

금지된 단축 경로:

```text
작업 사실 → 문장 다듬음 → CHANGELOG
```

### 6.1 절단선 (필수)

1. MILESTONE 커밋·diff·spec은 **증거**다. CHANGELOG 초안이 아니다.
2. 커밋에 필요한 구체성(`AppChat.vue 1532→160`, `JournalEntryResolver`, vitest↔gradle, §10/§11, migration 타깃 번호)은 커밋에 남겨도 되고, CHANGELOG로 자동 승격되지 않는다.
3. CHANGELOG 항목은 증거에서 **다시 쓴다.** 복사·번역 수준이 아니라 정보손실을 거친 재작성이다.

### 6.2 삭제 판정 (중심 규칙)

각 후보 항목에 묻는다.

> **이 항목을 몰라도, 사용자가 이 버전의 제품 변화를 이해하는 데 지장이 없는가?**

- **지장 없음 → CHANGELOG에서 삭제한다.**
- **지장 있음 → 사용자/제품 언어로만 남긴다.** 구현 식별자는 제품 의미를 가리킬 때만 예외적으로 쓴다.

예:

| 커밋/증거에 있는 말 | CHANGELOG |
|---------------------|-----------|
| `AppChat.vue(1532→160)` | 삭제 (제품 변화 정보 ≈ 0) |
| `JournalEntryResolver` 추출 | 삭제 |
| vitest를 gradle check에 연결 | 삭제 |
| §10 squash, §11 멀티 에이전트 규율 | 삭제 (개발 규율 일지) |
| 완료를 `RESOLVED` 전이로 처리 | **완료한 할 일을 지우지 않고 완료로 남겨 다시 보거나 되돌릴 수 있다** 로 재작성. enum 이름은 버려도 됨 |

### 6.3 버릴 것 / 살릴 것

**버린다 (기본값)**

- 파일·클래스·컴포넌트·줄 수·리팩터 분해 수치
- 테스트·CI·게이트·빌드 배선 (사용자 체감이 없으면)
- 개발 규율·문서 정비·스펙 정리·archaeology 기록
- 내부 API·스토어·컴포저블·패키지 이동 (계약이 사용자/배포에 안 보이면)
- SAVEPOINT 과정, 시행착오, import/포맷/오탈자
- “구조 정리”, “개발 규율·문서”를 채우기 위한 항목

**살린다**

- 새로 할 수 있게 된 일
- 기존 사용 흐름·화면 동작의 변화
- 체감되는 성능·안정성·보안 개선 (실측이 있으면 조건과 함께)
- 데이터 의미·권한·호환처럼 사용자가 알아채는 계약 변화

**예외로 살린다 — `운영 / 주의사항`만**

사용자 기능은 아니지만 배포·운영에 치명적이면 별도 소절에만 적는다.

- 수동 DB migration, 호환 깨짐, 필수 설정 변경, 데이터 백필
- 한 줄로 “무엇을 해야 하는가”만. 구현 경로·클래스명은 넣지 않는다.

### 6.4 작성 시점

1. 릴리스에 넣을 MILESTONE squash를 마친다.
2. 증거(커밋 로그·최종 diff·spec·실측)를 모은다. **초안으로 붙여 넣지 않는다.**
3. §6.2 삭제 판정으로 항목을 걸러 `docs/CHANGELOG.md`에 다시 쓴다.
4. 버전 문자열·릴리스 게이트를 확인한다.
5. CHANGELOG는 릴리스 문서용 마지막 독립 커밋으로 확정한다.

작업 중 CHANGELOG를 SAVEPOINT마다 갱신하지 않는다.

### 6.5 분량 · 분류

- 릴리스당 **한 화면~한 페이지**를 넘기지 않는 것을 기본으로 한다. 넘치면 삭제 판정을 다시 적용한다.
- 쓰는 분류만 쓴다. 빈 칸을 채우지 않는다.

| 분류 | 기준 |
|------|------|
| 신규 기능 | 사용자가 새로 할 수 있는 일 |
| 개선·사용성 | 기존 기능의 사용성·성능·안정성 |
| 버그 수정·정합성 | 깨져 있던 동작의 복구 |
| 운영 / 주의사항 | 배포·호환·수동 절차 (해당 시만) |
| 기술적 마일스톤 | 프로젝트의 기술 세대·플랫폼·운영 방식이 바뀐 전환점 (해당 시만) |

기본 분류(`신규 기능 / 개선·사용성 / 버그 수정·정합성`)는 **주 표면(현재 Web)**을 무표지로 서술한다. 그 외 사용자가 구별하여 소비하는 **독립 제품 표면**(Mobile 등)은 해당 릴리스에 의미 있는 변화가 있을 때만 **표면명 섹션**으로 분리한다. 표면 구분은 제품 표면축이지 구현 축이 아니다 — 새 표면(Desktop 등)이 생겨도 이 규칙으로 설명한다.

`구조 정리`, `개발 규율·문서`, `스키마`를 일반 분류로 두지 않는다. 스키마·배포가 운영자에게 필수면 `운영 / 주의사항`으로만 흡수한다. 기술 세대·플랫폼·운영 방식의 전환점만 조건부 `기술적 마일스톤`으로 별도 기록한다 — 구현 세부는 아니다(§6.7).

`성능`과 `구조`는 한 분류로 묶지 않는다 — CHANGELOG 관점에서 운명이 반대다. 사용자가 관찰 가능한 **성능 결과**(예: 검색 응답이 크게 빨라짐)는 `개선·사용성`에 넣고, `ChatOrchestrator 분해`·`API client 수렴` 같은 **구조적 수단**은 중요도와 무관하게 CHANGELOG에서 제외한다(Git 커밋이 원장).

### 6.6 표현

- 주어는 제품·사용자 경험이다. 모듈·PR·에이전트 작업 일지가 아니다.
- 실측 수치는 같은 조건의 전후가 있을 때만 적는다.
- 한 사용자 효과를 여러 분류에 중복하지 않는다.

### 6.7 압축기의 금지선 — 압축기는 보존-또는-삭제만 한다

CHANGELOG 압축기는 증거에 있는 관찰 가능한 사실을 보존하거나 삭제한다. 증거에 없는 것을 발견·발명·재합성하지 않는다. 아래는 그 선을 넘는 대표 유형이다.

- **운영 요구 발명 금지.** `운영 / 주의사항`은 원자료에 릴리스 소비자의 행동 요구가 명시된 경우에만 보존한다. 구현 사실(마이그레이션 파일 존재·수동 적용 등)에서 "먼저 적용해야 한다"는 요구를 추론해 만들지 않는다. 새 운영 note가 필요하면 그것은 압축이 아니라 별도 저작 행위이며 자체 근거를 갖춘다.
- **관찰 가능성은 생존의 필요조건이지 충분조건이 아니다.** 관찰 가능한 변화 중 §6.2의 삭제 판정을 통과한 것, 즉 그 릴리스의 제품 차이를 이해하는 데 필요한 것만 살린다. 1px 조정·툴팁 문구·간격 같은 작은 동종 변화는 관찰 가능해도 상위 항목에 흡수하거나 버린다. 변화의 크기는 생존 여부가 아니라 세분화(별도 항목 / 흡수 절 / 삭제)를 정한다.
- **살아남은 독립 의미는 억지로 합치지 않는다.** 삭제 판정으로 버릴 것을 버린 뒤, 남은 서로 다른 제품 의미를 분량을 줄이려고 한 문장에 합치지 않는다. 압축률은 목표가 아니며, 억지 병합은 관계변조를 다시 부른다(관계 불변 참조). 특히 같은 화면·도메인에 속한다는 이유만으로 독립된 제품 변화를 한 항목에 묶지 않는다. 병합은 공통된 제품 의미가 있을 때만 한다.
- **원 분류는 증거일 뿐 새 분류를 구속하지 않는다.** 소급 정제는 과거 분류를 압축하는 작업이 아니라 원문 항목을 제품 의미로 재분류하는 작업이다. 원문이 둔 카테고리를 신뢰하지 않는다(예: 원문이 `버그 수정`에 둔 "모달을 드래그로 옮길 수 있다"는 실제로 `개선·사용성`이다).
- **소급 정제는 당시 사료로만 복원한다.** 과거 릴리스에서 삭제·모호 항목을 되살리려면 그 시점의 사료(당시 Git·이슈·문서)를 근거로만 복원한다. 현재 기억이나 사후 추정으로 과거 릴리스의 의미를 보강하지 않는다.
- **관계 불변.** 압축은 정보손실을 허용하되 사건 간 인과·주체 관계를 변조하지 않는다. 서로 다른 사건을 하나로 합치면서 원인·주체를 바꾸지 않는다(예: "엔트리 삭제 → 태그 클라우드 갱신"을 "리플렉션 수정 → 태그 클라우드 갱신"으로 옮기지 않는다).
- **구현 규모는 제품 효과의 증거가 아니다.** 변경의 범위·난이도·작업량이 크다는 이유만으로 성능·안정성·보안·정합성 등의 제품 효과를 추론하지 않는다. 여러 구현 변경을 하나의 제품 결과로 압축하려면 원자료가 그 결과를 직접 뒷받침해야 한다.
- **성능.** 관찰 가능한 효과가 특정되면 실측 수치가 없어도 살린다(예: 열 때 매 행 요청을 한 번에 조회로 바꿔 화면이 빨리 열린다). 구현 사실만 있고 관찰 효과가 특정되지 않으면 삭제한다. 여러 성능 최적화는 원자료가 동일한 관찰 가능한 성능 결과를 뒷받침할 때만 하나의 결과 항목으로 압축한다.
- **기술적 마일스톤은 세대 전환만, 경계에서 한 번 적는다.** CHANGELOG는 제품 독자와 함께 포트폴리오 독자도 갖는다. 프로젝트의 기술 세대·플랫폼·운영 방식이 바뀐 전환점(예: 템플릿 SSR→Vue SPA, 런타임·언어 세대, 배포 인프라 이전, 마이그레이션 도구 도입)은 `기술적 마일스톤`으로 정직하게 기록한다. 단 ①구현 난이도·작업량으로는 자격이 없고(구현 규모≠근거) ②제품 변화인 척하지 않으며 ③여러 릴리스에 걸친 전환은 세대 경계를 넘는 릴리스에 한 번만(도입 또는 완료) 적는다. 서비스 분리·패키지 재정렬·URL 정리·라이브러리 적용 같은 구현 세부는 마일스톤이 아니다.
- **내부 변경 릴리스도 버전 경계는 보존한다 (항목 삭제 ≠ 릴리스 삭제).** 실제 변경은 있으나 삭제 판정·기술적 마일스톤 판정 후 서술할 항목이 남지 않으면, 릴리스 헤더를 유지하고 `내부 변경만 포함.`으로 표시한다. 삭제된 구현 내용을 대신 요약해 빈칸을 채우지 않는다. 변화 없음과 기록 대상 변화 없음은 다르다.
