# Board, User 도메인 패키지/네이밍 설계 결정 기록
(2026.04.18)

## 1. 문제 배경
Board, User 도메인 설계 과정에서 다음 충돌이 발생함:
- 테이블/도메인 네이밍: 
  - board, user가 가장 자연스럽고 정합성이 높음
- Java 패키지 구조: 
  - board, board.post, board.notice 등 동일 aggregate를 같은 패키지 아래에 묶어둘 경우: board의 경우 root에 위치하게 됨 → 패키지 구조 난장판
  - 별도의 aggregate를 둘 경우: 도메인과 패키지 불일치.
  - 동일 네이밍 반복할 경우 → board.board.Board, user.user.User 형태의 중복 발생
    
즉, 
- 패키지명과 핵심 엔티티명이 동일할 때 구조적으로 발생하는 도메인 언어 정합성 vs 패키지 구조 정합성 충돌.
- "이 문제는 Spring 공식 문서나 업계 표준도 명확한 해결책을 제시하지 않는 고질적 문제다."

## 2. 설계 기준
### 2.1 
- 도메인 언어 정합성 기준으로 가면(Board, User): 패키지 구조 정합성이 손실된다.
- 패키지 구조 정합성 기준으로 가면(board.def, user.account): 도메인 언어 정합성이 손실된다. 

- "어긋남은 반드시 어딘가에서 흡수해야 한다. 흡수 위치를 의식적으로 선택하는 것이 설계다."
- "이 문제는 “정답 찾기” 문제가 아니라 트레이드오프 선택 문제다." 
- 초기 가설: “정합성 총량을 기준으로 판단한다.” → 수정된 결론: "정합성은 총량/균등 분배가 아니라 우선순위로 유지한다."

### 2.2 우선순위
- 1순위: 도메인 언어 (최우선) — DB, 코드, API, 문서, 팀 대화 전 영역의 공통 기준.
  - "도메인 언어는 왜곡하지 않는다. 구조에서 타협한다."
  - board, user는 도메인 언어로 유지해야 한다.
- 2순위: 패키지 구조 — 리팩토링 가능. 패키지에서 구조적 충돌을 흡수.
  - board, user 하에 root 엔티티를 두는 보조 패키지를 둔다.
  - "완벽한 단어는 존재하지 않는다. → '덜 어긋나는 단어'를 선택해야 하는 문제다."
  - "이름이 완벽해서 사용하는 게 아니라, 우리가 그렇게 부르기로 약속했기 때문에 의미가 생기는 것이다."
- 3순위: 기술 네이밍 — Entity suffix 등. 가장 낮은 우선순위.
  - 의미 없는 suffix(Def, Info 등)는 지양한다.
  - 네이밍 문제는 일정 수준에서 강제 종료한다.
- "도메인 언어를 기준으로 고정하고, 구조에서 불편을 흡수한다."

## 3. 최종 결정
### 4.1 테이블
- board / board_post / ...
- user / user_signup_request / ...
### 4.2 클래스/패키지 구조
- BoardEntity / package board.group
- UserEntity / package user.account
### 4.3 결정 이유
- group은 특정 도메인 의미를 강하게 갖지 않는 중립적 단어다.
- channel, section 등은 의미적 왜곡 가능성이 존재한다.
- group은 “게시글의 묶음 단위”라는 최소 의미만 전달하며, 도메인과 충돌하지 않는다.
- 따라서 구조 충돌을 흡수하는 패키지명으로 가장 안전한 선택이다.
