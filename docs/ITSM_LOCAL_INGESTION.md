# ITSM 로컬 적재 작업 계약

## 1. 명령 해석

사용자가 **`itsm.idstrust.com` 목록 또는 상세 링크와 함께 `ITSM 적재해` 또는 `istm 적재해`라고 명시하면**, 대소문자와 무관하게 해당 요청을 아래 정형 작업 전체에 대한 실행 승인으로 해석한다.

- 사용자가 제공한 SSO 인증 URL로 현재 브라우저 세션의 인증 상태를 확인한다.
- 지정된 ITSM 목록을 마지막 페이지까지 읽고 각 항목 상세와 첨부 메타데이터를 조회한다.
- 항목 원문과 메타데이터를 로컬 Markdown 파일로 저장한다.
- 이미지 첨부파일의 원본을 CSR별 디렉터리에 저장한다.
- 해당 목록 미러의 `index.json`을 동기화하고 아래 검증 절차를 완료한다.

대상 링크로 목록과 범위를 하나로 확정할 수 있는 정형 요청에는 `AGENTS.md`의 일반적인 수정 직전 승인 질문을 다시 적용하지 않는다. 대상 목록, 범위 또는 저장 위치를 하나로 확정할 수 없는 경우에만 질문한다.

`ITSM 적재해`는 현재 요청 링크가 가리키는 목록을 범위로 삼는다. 화면의 다른 단계 탭, 다른 처리 메뉴, 검색 결과 또는 통계 화면까지 범위를 확장하지 않는다. 사용자가 상세 링크 하나를 지정하면 해당 CSR 하나만 적재한다.

`전체 ITSM 적재해` 또는 `전체 istm 적재해`는 다음 세 조회 원장을 전수 적재하는 명령이다.

- CSR조회: `itsmSearchList.dmn`
- 장애처리조회: `troubleSearchList.dmn`
- 이슈처리조회: `issueSearchList.dmn`

전수 적재의 기간은 각 목록에서 제공하는 날짜 조건의 시작일을 `2000-01-01`, 종료일을 실행 당일로 설정한다. 목록이 더 이른 기록을 반환하거나 서비스의 지원 시작일을 별도로 제공하면 실제 반환 범위를 기준으로 보존한다. 처리 화면의 작업 큐와 마이페이지 목록은 이 세 원장의 부분집합으로 취급하며 별도 전수 범위에 더하지 않는다.

- 단순 권한·Role·롤 코드의 신청, 요청, 부여, 해제, 삭제, 회수, 변경, 취소

정책·Parameter·메모리·증설·목록 추출·현황·분석·감사, 서비스·배치·인터페이스·RFC·통신·연계 계정, 디버깅·개발·품질 서버·프로그램·T-CODE·CDS·프로젝트·CTS·이관·릴리즈가 제목에 나타나는 기술 작업은 BC 반복 운영 제외 대상에서 보존한다.

모든 시스템에서 제목으로 식별되는 비밀번호·잠금 해제, 사람 사용자 계정의 생성·발급·등록·삭제·폐기·중지·비활성화, 단순 클라이언트 설치 요청과 단순 사용자 권한의 신청·요청·부여·추가·해제·삭제·회수·변경·취소·등록은 반복 운영 항목으로 제외한다. 정책·Parameter·메모리·증설·감사, 서비스·배치·인터페이스·RFC·통신·연계 계정, 디버깅·개발·품질 서버·프로그램 수정·개선·개발, T-CODE·CDS·프로젝트·CTS·이관·릴리즈·로직·오류·에러·장애가 제목에 함께 나타나는 항목은 기술 작업으로 보존한다. 권한 항목에서 매핑·이력·현황·조회·추출·분리·설계·체계·프로세스·원인·조치와 메뉴·기능 변경이 함께 나타나는 경우도 기술 또는 구조 변경 작업으로 보존한다.

분기·반기·연간·정기 또는 ITGC 계정·권한 모니터링과 점검을 위한 반복 자료·목록 추출 요청은 제외한다. 단순 프로그램 설치·설치 문의·재설치 요청도 제외한다. 로그인·접속 실패는 사용자 계정 문제와 인증 연동·서비스 장애를 제목만으로 구분할 수 없으므로 이 반복 운영 제외 규칙에 포함하지 않는다.

### 1.1 로컬 보존·삭제 계약

현재 ITSM 원격 적재는 종료된 상태이며 이 절은 이미 저장된 폐쇄형 로컬 아카이브의 보존·삭제에 적용한다. 로컬 미러의 삭제 판단은 문서 자체의 독립 보존 가치와 동일 시스템 안에서의 반복 운영 패턴 가치를 분리하여 수행한다. 단일 중요도 점수, 제목 키워드, 본문 길이, 처리 결과 유무 또는 처리 결과의 상세도만으로 삭제하지 않는다.

다음 LIMS 관련 원문은 개별 중요도와 반복 빈도에 관계없이 보존한다.

- 원격 시스템이 `LIMS`, `LimsPro`, `NEW LIMS`인 항목
- 다른 시스템에 속하더라도 요청 내용·처리 내역·처리 결과가 LIMS의 기능, 데이터, 인터페이스, 장애 또는 업무 절차를 직접 다루는 항목

비LIMS 항목 중 핵심 장애의 재현 조건·영향·원인·조치가 드러나는 티켓, 시스템 설계와 인터페이스, 데이터 흐름, 업무 규칙, 예외 조건, 마이그레이션과 중요 변경의 근거가 되는 티켓은 발생 빈도와 관계없이 개별 원문을 보존한다. 단 한 건뿐이라는 사실은 삭제 사유가 아니다.

다음 항목은 그 표현만으로 삭제하지 않고, 개별 원문보다 집합적 운영 패턴의 가치를 평가하는 운영성 후보로 분류한다.

- 계정·권한·비밀번호·담당자 변경
- 데이터 수정·삭제·추출
- 처리 결과가 없거나 `완료했습니다`와 같은 짧은 결과만 있는 문서
- 테스트·중복·재문의
- 개인 PC·클라이언트 설치·접속 지원
- 특정 건의 값만 바꾸는 일회성 작업

운영성 후보가 동일 시스템에서 기간을 두고 반복되거나 전체 요청에서 두드러진 비중을 차지하면 개별 티켓 묶음은 운영 패턴으로 취급한다. 패턴에는 대상 시스템, 정규화한 요청 유형, 발생 건수, 최초·최종 발생일, 기간별 추이, 반복 대상, 처리 방식과 그 패턴이 드러내는 수동 운영·동기화·셀프서비스·기록 품질·배포 또는 지원 구조를 기록한다. 패턴 기록과 원본 티켓 식별자의 대응을 검증한 뒤 해당 묶음의 개별 원문을 삭제할 수 있다.

운영성 후보가 같은 시스템에서 반복 패턴을 이루지 않고 독립 보존 가치도 없으면 개별 원문을 삭제할 수 있다. 반복 패턴을 이루더라도 핵심 장애·설계·업무 규칙에 해당하는 예외 티켓은 패턴 묶음에 흡수하지 않고 원문을 보존한다.

로컬 삭제는 다음 순서로 수행한다.

1. LIMS 보호 대상과 비LIMS 독립 보존 대상을 먼저 확정한다.
2. 나머지 운영성 후보를 시스템별로 군집화하고 반복 패턴 여부를 판정한다.
3. 반복 패턴은 집계 문서를 먼저 저장하고 원본 식별자·건수·기간과의 대응을 검증한다.
4. 독립 보존 가치가 없고 검증된 패턴으로 대체된 반복 원문과 패턴을 이루지 않는 단순 원문만 삭제한다.
5. 삭제한 Markdown과 첨부파일을 `index.json`, `checkpoint.json` 및 파생 중요도·검색 인덱스에서도 제거하고 실제 파일 수와 인덱스 항목 수를 다시 대조한다.

패턴 집계가 없거나 검증되지 않은 상태에서는 반복 운영 원문을 일괄 삭제하지 않는다. 중요도 인덱스는 검토 순서를 정하는 보조 자료이며 보존·삭제의 단독 근거로 사용하지 않는다.

## 2. 인증과 비밀정보

- 인증이 필요하면 사용자가 제공한 `newMemberLoginSSOchk.dmn` URL을 브라우저에서 연 뒤 대상 목록으로 이동한다.
- 인증 URL은 세션 진입에만 사용한다. URL 전체, 쿼리 문자열, `ssokey`, 쿠키, 로컬 저장소와 세션 저장소의 값을 읽거나 로컬 파일·로그·인덱스·완료 보고에 기록하지 않는다.
- 제공된 SSO URL이 인증에 실패하면 로그인 정보를 추정하거나 다른 계정으로 우회하지 않고 중단한다.
- 인증된 화면에서 읽을 권한이 없는 CSR에는 빈 파일이나 추정한 placeholder를 만들지 않는다.

## 3. 기본 저장 위치와 파일명

1. CSR 기본 저장 위치는 `daily/text/raw/itsm/csr/{안전한 원격 시스템명}/`이다.
2. 장애 기본 저장 위치는 `daily/text/raw/itsm/trouble/{안전한 원격 시스템명}/`, 이슈 기본 저장 위치는 `daily/text/raw/itsm/issue/{안전한 원격 시스템명}/`이다. 원격 시스템명이 비어 있으면 `_시스템미지정`을 사용한다.
3. 원격 시스템명은 의미가 유사해도 병합하거나 정규화하지 않는다. Windows 폴더명 금지문자만 대응하는 전각 문자로 치환하여 원격 분류와 일대일로 보존한다.
4. 항목별 파일명은 `{원격 표시번호}__{안전한 원격 제목}.md` 형식을 사용한다. 표시번호가 없는 항목은 `docno`를 식별 파일명으로 사용하고 인덱스에 표시번호 부재를 기록한다.
5. 원본 저장 대상 이미지 첨부파일은 해당 시스템 경로의 `attachments/{원격 표시번호 또는 docno}/`에 원격 파일명 그대로 저장한다.
6. Windows 파일명에 사용할 수 없는 문자는 정보 손실이 가장 적은 전각 문자 또는 `_`로 치환한다.
7. 파일명 끝의 마침표와 공백은 제거하고, 과도하게 긴 파일명은 원격 표시번호 또는 `docno`를 보존한 채 제목 부분만 줄인다.
8. 동일 표시번호의 파일이나 인덱스 항목이 이미 있으면 일반 적재 요청으로 덮어쓰지 않는다. 사용자가 `갱신`, `다시 적재`, `재적재`처럼 원격 현재 상태로 교체할 의사를 명시한 경우에만 갱신한다. 전수 적재 명령은 아래 전수 병합 계약에 한해 기존 부분 미러의 검증·병합을 승인한다.
9. 동일 표시번호에 서로 다른 `docno`가 관측되거나 동일 `docno`가 서로 다른 표시번호에 연결되면 식별자 충돌로 중단하고 어느 쪽도 덮어쓰지 않는다.

## 4. 목록 조회 계약

- 대상 목록의 화면 표시 총 건수, 현재 검색 조건, 처리 단계와 페이지당 건수를 먼저 기록한다.
- 화면이 허용하는 최대 페이지당 건수를 사용하고 첫 페이지부터 마지막 페이지까지 순서대로 조회한다.
- 각 행에서 원장 종류, 원격 표시번호, 고객사, 시스템명, 처리유형, 처리단계, 제목, 요청자, 요청일, 완료일 또는 완료예정일, 처리자, 처리상태, 첨부 표시와 상세 URL의 `docno`를 화면에 존재하는 범위에서 수집한다.
- 원격 표시번호와 `docno`는 별도 식별자로 보존한다. `docno`가 없으면 상세를 추정하지 않고 해당 행을 조회 실패로 기록한다. 원격 표시번호가 없는 행은 `docno`를 로컬 식별자로 사용한다.
- 페이지별 행 수의 합계, 고유 `docno` 수와 화면 표시 총 건수를 대조한다.
- 페이지 이동 중 정렬·검색 조건·처리 단계 또는 총 건수가 바뀌면 일관된 목록 스냅샷으로 간주하지 않고 쓰기를 중단한다.
- 동일 `docno`가 여러 페이지에 나타나고 페이지 번호를 제외한 표시번호·목록 메타데이터·상세 URL이 모두 같으면 페이지 경계 이동 중복으로 판정한다. 최초 행을 기준선에 유지하고 관측된 페이지를 `paginationDuplicates`에 기록한다. 어느 하나라도 다르면 식별자 충돌로 검증 실패 처리한다.

### 4.1 전수 목록 기준선과 종료 증분

- 전수 적재 시작 시 세 원장을 각각 첫 페이지부터 마지막 페이지까지 조회하여 표시 총 건수, 페이지별 행, 표시번호, `docno`, 상세 URL과 목록 메타데이터의 기준선을 만든다.
- 기준선은 각 원장 경로의 `checkpoint.json`에 기록하고 상세 수집 재개의 단일 기준으로 사용한다.
- 장시간 수집 중 원격 순서가 바뀌어도 진행 중인 기준선의 상세 대상은 바꾸지 않는다.
- 기준선 상세 수집이 끝나면 같은 날짜 범위의 첫 페이지부터 다시 조회하여 새 `docno`와 갱신된 목록 메타데이터를 확인한다. 새 항목은 증분 대상으로 합류시키고, 기존 항목의 변경은 현재 원격 상세로 한 번 다시 수집한다.
- 종료 증분까지 완료된 시점의 고유 항목 수를 최종 `index.json` 범위로 기록한다. 최초 기준선 건수와 종료 증분 건수는 별도 필드로 보존한다.

## 5. 상세와 첨부파일 조회 계약

- 목록에서 확인한 상세 URL을 사용하며 처리단계에 따라 달라지는 상세 화면 경로를 임의로 고정하지 않는다.
- 상세 화면에서 원장별 등록 정보, 요청 내용, 현재 처리 정보, 화면에 제공되는 처리 내역과 처리 결과를 원문 순서대로 보존한다.
- 상세 본문은 `#container` 내부의 등록·처리 단계에서만 추출하고 `script`, `style`, 공통 헤더·메뉴·푸터는 저장하지 않는다. 요청 내용과 각 처리 단계 및 결과 필드는 화면의 개별 영역에서 각각 추출하며 한 영역의 전체 텍스트를 여러 Markdown 섹션에 복제하지 않는다.
- 등록 정보는 원장 종류, 표시번호, 제목, 회사, 시스템, 요청자, 요청자 부서, 요청자 이메일, 요청일, 고객완료요청일, 처리자, 진행사항 공유자와 화면이 제공하는 유형을 포함한다. 화면에 없는 필드는 빈 값으로 만들지 않고 생략한다.
- 처리 내역은 단계명, 발생 시각, 처리자, 업무구분, 처리구분, 요청유형, 완료예정일과 단계별 본문을 화면에 나타난 범위에서 보존한다.
- 목록과 상세의 표시번호가 다르거나 상세 URL의 `docno`가 요청한 값과 다르면 해당 항목을 저장하지 않는다. 목록에 표시번호가 없는 항목은 상세의 `docno` 일치만 검증한다.
- 본문은 요약·교정·번역하지 않는다. 화면의 레이아웃용 반복 공백은 줄일 수 있지만 문장, 표 값과 줄바꿈의 의미는 보존한다.
- 모든 첨부파일은 파일명, 확장자, 원격 표시 크기와 원격 다운로드 URL에서 `ssokey`를 제외한 공개 식별 부분을 보존한다.
- 원본 저장 대상은 파일명의 마지막 확장자가 대소문자 구분 없이 `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`인 이미지이다. 해당 이미지는 원본 바이트를 다운로드하고 로컬 상대 경로와 SHA-256을 기록한다.
- PDF, Word, Excel, PowerPoint, HWP, ZIP, 동영상 및 그 밖의 형식은 원본을 다운로드하지 않고 `metadata_only`로 기록한다. 제외된 파일은 적재 실패나 첨부 차단으로 집계하지 않는다.
- 같은 항목에 동일한 원격 파일명이 여러 개 있으면 이미지 원본을 덮어쓰지 않고 순번을 붙이며 원격 링크와 SHA-256으로 각각의 대응을 보존한다.
- 원본 저장 대상 이미지를 읽지 못해도 검증된 CSR 본문과 첨부 메타데이터는 저장할 수 있다. 해당 인덱스 항목을 `ATTACHMENT_BLOCKED`로 표시하고 실패한 파일명과 실패 단계를 기록하여 다음 재적재에서 다시 시도한다.
- 이미지 원본 저장 정책 이전에 내려받은 비이미지 파일은 자동 삭제·이동·재해시하지 않는다. 해당 경로는 인덱스의 `legacyPreservedFiles`에 별도로 등재하고 현재 수집의 이미지 원본 수와 `metadata_only` 수에서 제외한다.

## 6. Markdown 저장 형식

각 원장 항목 파일은 다음 현재 미러 형식을 따른다.

1. 제목: `# {원격 표시번호 또는 docno} {제목}`
2. 메타데이터: `sourceType`, `sourceUrl`, `displayNumber`, `docno`, `status`, `system`, `requester`, `requesterDepartment`, `requesterCompany`, `requesterEmail`, `requestedAt`, `requestedCompletionAt`, `completedAt`, `assignee`, `requestType`, `fetchedAt`
3. `## 요청 내용`: 상세 화면의 요청 원문
4. `## 처리 내역`: 화면에 제공되는 단계별 시각·메타데이터와 본문
5. `## 처리 결과`: 화면에 제공되는 결과 원문
6. `## 첨부파일`: 모든 첨부의 파일명, 확장자, 표시 크기, 원격 URL과 저장 상태. 저장 대상 이미지는 로컬 상대 경로와 SHA-256을 함께 기록하고 그 밖의 형식은 `metadata_only`로 기록한다.

파일은 UTF-8 BOM 없음으로 저장한다. 화면에 해당 데이터가 없더라도 `요청 내용`, `처리 내역`, `처리 결과`, `첨부파일` 섹션은 유지하고 `없음`으로 표시한다. 이름·이메일·업무 요청 원문은 원격 기록을 보존하기 위한 원문 데이터이며 테스트·spec·예시·시드 데이터로 복사하지 않는다.

## 7. 인덱스 계약

각 원장의 `index.json`은 다음 정보를 가진다.

- `sourceUrl`: 쿼리 문자열에서 인증정보를 제거한 대상 목록 URL
- `listName`, `listStatus`, `searchType`, `searchKeyword`, `displayedTotal`
- `collectedAt`, `scope`, `items`
- `scope`: 요청 범위, 조회 페이지 수, 조회 행 수, 고유 표시번호 수, 고유 `docno` 수, 성공 수, 조회 실패 수, 전체 첨부 메타데이터 수, 이미지 원본 수, `metadata_only` 수와 첨부 차단 수
- `items`: 원장 종류, 표시번호, `docno`, 제목, 시스템, 안전한 시스템 디렉터리, 처리단계, 요청자, 요청부서, 요청회사, 요청일, 완료일 또는 완료예정일, 처리자, 상세 URL, Markdown 상대 경로, 전체 첨부 수, 이미지 원본 수, `metadata_only` 수, 본문 SHA-256, 수집 상태와 수집 시각
- `baseline`: 최초 기준선의 수집 시각, 표시 총 건수, 페이지 수와 고유 `docno` 수
- `finalDelta`: 종료 증분 확인 시각, 신규·변경·누락 항목 수와 최종 고유 `docno` 수
- `paginationDuplicates`: 동일한 목록 항목이 여러 페이지 경계에서 관측된 `docno`와 페이지 목록
- `legacyPreservedFiles`: 현재 이미지 정책 이전에 저장되어 그대로 보존하는 비이미지 원본의 상대 경로 목록과 총 파일 수·바이트 수

인덱스를 쓰기 직전 최신 파일을 다시 읽고 다른 세션이 추가한 항목을 보존한다. 새 적재는 기존 표시번호나 `docno`와 충돌하면 중단하며, 갱신 요청은 대상 항목의 원격 현재 상태만 교체한다. 성공적으로 상세가 저장된 항목만 정상 항목으로 집계한다.

### 7.1 전수 병합과 재개

- 전수 적재는 기존 부분 미러의 각 Markdown SHA-256, 표시번호와 `docno`를 기존 인덱스와 먼저 대조한다.
- 기존 파일과 인덱스가 일치하고 전수 기준선에도 같은 표시번호·`docno`가 있으면 해당 항목을 전수 미러에 병합한다. 첨부 정책 등 현재 계약과 내용 형식이 달라 원격 재조회가 필요한 항목은 완료 항목으로 재사용하지 않는다.
- 기존 파일·인덱스·원격 기준선 중 식별자 또는 해시가 충돌하면 전수 쓰기를 시작하지 않는다.
- `checkpoint.json`에는 기준선 해시, 전체 대상 수, 다음 처리 위치, 성공·실패·첨부 차단 항목과 마지막 갱신 시각을 기록한다.
- 상세는 최대 4건을 동시에 조회하고 이미지 다운로드는 해당 상세 작업 안에서 수행한다. 완료 결과는 250건 단위로 합류시켜 체크포인트를 한 번 기록하며, 중단 시 마지막으로 완료된 묶음 다음 위치부터 재개한다.
- 중단 후 같은 전수 명령을 받으면 기준선 해시와 현재 `checkpoint.json`을 검증하고, 완료된 파일의 SHA-256이 일치하는 항목은 건너뛰어 다음 처리 위치부터 재개한다.
- 실패 항목은 전체 1차 순회가 끝난 뒤 개별 재시도한다. 재시도 후에도 실패한 항목은 원인과 단계가 있는 상태로 남기며 전체 적재 완료로 보고하지 않는다.
- 최종 `index.json` 검증과 종료 증분이 성공하면 `checkpoint.json`을 완료 상태로 유지하여 실행 범위와 재개 이력을 보존한다.

## 8. ITSM에서 허용되는 동작

적재는 **읽기 전용 수집**이다. ITSM에는 조회와 이미지 첨부파일 다운로드 외 상태 변화를 남기지 않는다.

허용:

- 사용자가 제공한 SSO URL을 통한 인증 확인
- 대상 목록과 페이지 조회
- CSR 상세와 처리 내역 조회
- 첨부 메타데이터 조회
- 원본 저장 대상 이미지 첨부파일 다운로드

금지:

- CSR·장애·이슈 생성·수정·삭제
- 접수·저장·임시저장·승인·완료·평가
- 담당자, 처리구분, 예정일, 공유자와 기타 업무 필드 변경
- 댓글·메모·처리 결과 작성
- 로그아웃, 계정·권한·개인정보 설정 변경

## 9. 사용하지 않는 우회 경로

- 인증 실패를 로그인 폼 자동 입력, 다른 계정, 쿠키 복사 또는 보안 경고 우회로 해결하지 않는다.
- 브라우저 쿠키·로컬 저장소·세션 저장소를 읽지 않는다.
- 로컬 DreamDiary API나 DB에 원문을 저장하지 않는다.
- 누락된 목록 행, 상세 필드, 처리 내역과 첨부파일을 추정하여 채우지 않는다.
- 페이지 일부만 성공한 결과를 전체 목록 적재 완료로 표시하지 않는다.

## 10. 완료 검증과 보고

1. 첫 조회와 마지막 조회의 목록명, 처리 단계, 검색 조건과 화면 표시 총 건수가 일치하는지 확인한다.
2. 원장별 페이지 행 수 합계, 고유 표시번호 수, 고유 `docno` 수, 상세 조회 대상 수와 화면 표시 총 건수를 대조한다.
3. 각 상세의 표시번호·`docno`가 목록과 일치하고 Markdown 파일이 존재하며 크기가 0보다 큰지 확인한다. 표시번호가 없는 항목은 `docno`와 파일명의 일치를 확인한다.
4. 각 파일의 제목, 요청 내용 첫 구간, 마지막 처리 내역 또는 처리 결과 구간을 UTF-8로 읽어 원문이 잘리지 않았는지 확인한다.
5. 모든 첨부 메타데이터가 Markdown과 인덱스에 있는지 확인한다. 이미지 원본의 실제 바이트 SHA-256이 Markdown과 인덱스 값에 일치하는지 확인하고, 그 밖의 형식은 로컬 원본 없이 `metadata_only`인지 확인한다. 실패한 이미지 첨부는 `ATTACHMENT_BLOCKED` 상태와 재시도 정보가 있는지 확인한다.
6. 원장별 `index.json`을 다시 파싱하고 `scope`의 성공·실패·전체 첨부·이미지 원본·`metadata_only`·첨부 차단 수가 실제 `items` 및 파일 수와 일치하는지 확인한다.
7. 전수 적재는 `checkpoint.json`의 기준선 해시·완료 위치와 `index.json`의 `baseline`·`finalDelta`를 대조하고 종료 증분 대상이 모두 반영됐는지 확인한다.
8. 인증 URL 전체, `ssokey`, 쿠키와 저장소 값이 대상 파일 및 diff에 없는지 확인한다.
9. `python scripts/check_encoding.py`로 UTF-8 게이트를 확인한다.
10. 다른 세션 소유의 워킹트리 변경이 유지됐는지 `git status --short`로 확인한다.
11. 결과 보고에는 원장별 저장 경로, 최초·최종 표시 총 건수, 성공·실패·첨부 차단 수, 전체 첨부 메타데이터 수, 이미지 원본 수, `metadata_only` 수, 보존 중인 레거시 파일 수와 검증 결과만 간결하게 남긴다. 인증 URL과 `ssokey`는 보고하지 않는다.
