# 저널 엔트리 일괄 태그 (아이디어)

## 문서 상태

| 항목 | 값 |
| --- | --- |
| 상태 | 아이디어 (계약 외부) |
| 대상 | 저널 엔트리 검색 결과의 태그 연결 일괄 추가·제거 |
| 현재 동작 spec 반영 | 대상 아님 |

이 문서는 구현 계약이 확정되기 전의 독립 아이디어 노트다. 현재 구조에서 확인한 사실과 구체화된 후보 범위를 기록하고, 선택이 필요한 사항은 열린 질문으로 구분한다. 이 문서의 구체성은 기능 합의나 시스템 계약을 의미하지 않는다.

## 목적

검색으로 의미 있는 엔트리 집합을 좁힌 뒤 각 엔트리를 하나씩 수정하지 않고 동일한 기존 태그를 추가하거나 제거할 수 있게 한다. 검색 조건이 대상 집합을 만들고, 사용자의 명시적 선택이 실제 변경 대상을 확정한다.

## 아이디어 범위

다음 항목은 현재 스케치가 전제하는 후보 범위다.

- 진입점은 `JournalEntrySearchPage`로 한정한다.
- 사용자가 검색 결과에서 선택한 엔트리만 변경 대상으로 삼는다.
- 태그 작업은 **기존 태그 연결 추가·제거**를 지원한다.
- 추가와 제거는 서로 구분된 명시적 작업이며, 토글 하나로 두 의미를 겸하지 않는다.
- 태그 집합 전체 교체, 일괄 신규 태그 생성, 태그 마스터 삭제는 이 기능의 범위에 포함하지 않는다.
- 같은 검색 화면 세션에서 마지막으로 성공한 일괄 작업 1건의 실제 변경분을 한 번 되돌릴 수 있다.
- 일간·주간·월간·결산·스레드 화면에는 일괄 선택 UI를 추가하지 않는다.

## 현재 구조에서 확인한 사실

### 검색

- 검색 조건의 단일 진실 원천은 `JournalEntrySearchPage`의 URL query다.
- 검색 API는 `GET /api/journal/entries`이며 일기와 꿈을 한 번에 섞지 않고 요청 `type`으로 구분한다.
- 검색 결과는 `JournalEntryDto[]`이고 각 엔트리의 현재 태그 목록을 포함한다.
- 검색 결과에는 별도 페이지 선택 상태나 일괄 작업 상태가 없다.

### 태그 저장

- 태그 마스터는 `tag`, 엔트리 연결은 `tag_content(tag_id, ref_id, ref_content_type, created_by)`에 저장한다.
- `TagProcService`는 엔트리 하나의 현재 태그 집합과 요청 태그 집합을 비교해 추가·삭제하는 단건 전체 동기화 흐름이다.
- 일괄 추가·제거 API와 여러 엔트리의 태그 연결을 한 번에 검증·저장하는 서비스는 없다.
- `tag_content` 전체 스키마에는 `(tag_id, ref_id, ref_content_type, created_by)` 유니크 제약이 없다.
- `TagContentEntity`는 `@SQLDelete`를 사용하지만 `deleteObsoleteTagContents`의 JPQL bulk delete 경로도 존재한다. 연결 삭제의 보존 계약은 일괄 기능과 별개로 명확한 단일 정책이 필요하다.

### 파생 데이터와 후처리

- 저널 태그 변경은 사용자·콘텐츠 타입·기간별 태그 목록, 건수, 카테고리 캐시에 영향을 준다.
- 현재 `JournalTagCacheUpdtWorker`는 단건 저장의 연·월 문맥으로 캐시를 무효화한다.
- 임베딩 텍스트와 payload는 태그를 검색 가중치가 있는 의미 신호로 포함한다.
- 엔트리 등록·수정 흐름은 커밋 후 엔티티 추출과 임베딩 큐를 갱신하지만, 태그 연결만 일괄 수정하는 독립 후처리 경로는 없다.

### 데이터 현황

2026-08-15 운영 DB의 활성 데이터 집계는 다음과 같다. 태그명이나 저널 본문은 조회하지 않았다.

| 유형 | 엔트리 | 무태그 | 엔트리당 평균 태그 | 활성 연결 | 사용 중인 태그 종류 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 일기 | 3,677 | 956 (26.0%) | 1.75 | 6,444 | 267 |
| 꿈 | 5,381 | 2,380 (44.2%) | 1.70 | 9,157 | 1,013 |

추가로 확인된 데이터 불변식 이탈은 다음과 같다.

- 꿈 엔트리의 동일 `(ref_content_type, ref_id, tag_id)` 활성 연결 중복 1건
- `tag_content.ref_content_type`이 비어 있는 행 1건
- `created_by`, `tag_id`, `ref_id`가 비어 있는 행은 없음

## 작업 흐름 스케치

아래 흐름은 아이디어 범위를 사용자 작업으로 풀어쓴 것이다. 화면 배치와 선택 상한은 열린 질문이다.

1. 사용자가 검색 조건으로 일기 또는 꿈 결과를 좁힌다.
2. 검색 결과 중 변경할 엔트리를 명시적으로 선택한다.
3. 현재 검색 유형에서 사용 중인 기존 태그 중 하나 이상을 선택한다.
4. 추가 또는 제거 작업을 명시적으로 선택한다.
5. 적용 전 선택 엔트리 수와 태그 수, 예상 추가·제거 연결 수, 변경 없는 연결 수를 확인한다.
6. 서버가 요청 전체를 검증하고 실제로 필요한 태그 연결만 추가하거나 제거한다.
7. 성공 응답 후 현재 검색 조건으로 결과를 다시 조회하고 마지막 작업의 Undo를 제공한다.

## 쓰기 경계 후보

다음 항목은 구현 전에 결정을 완료해야 하는 후보 계약이다.

### 요청 식별자

API 후보:

```text
POST /api/journal/entries/tags/bulk
POST /api/journal/entries/tags/bulk/undo
```

요청 DTO 후보:

```json
{
  "operation": "ADD",
  "contentType": "JOURNAL_DREAM",
  "entryIds": [101, 102],
  "tagIds": [11, 12]
}
```

응답 DTO 후보:

```json
{
  "operation": "ADD",
  "requestedEntryCount": 2,
  "requestedTagCount": 2,
  "changedLinkCount": 3,
  "unchangedLinkCount": 1,
  "affectedEntryCount": 2,
  "changedPairs": [
    { "entryId": 101, "tagId": 11 },
    { "entryId": 101, "tagId": 12 },
    { "entryId": 102, "tagId": 12 }
  ]
}
```

적용 요청은 선택 엔트리와 선택 태그의 조합을 표현하고, Undo 요청은 실제 변경된 연결 쌍만 역연산해야 한다. 위 API 경로·필드명과 Undo payload 직렬화 방식은 아직 구현 계약이 아니다.

### 검증 순서

서버 쓰기 경계는 최소한 다음 항목을 검증해야 한다.

- `entryIds`와 `tagIds`가 비어 있지 않은지
- 중복 ID를 제거한 뒤 요청 상한 안인지
- 모든 엔트리가 존재하고 요청 `contentType`과 일치하는지
- 모든 엔트리가 현재 로그인 사용자의 소유인지
- 모든 엔트리가 일자 완결 축의 쓰기 정책을 만족하는지
- 모든 태그가 존재하고 현재 사용자의 요청 콘텐츠 타입 태그 목록에 속하는지

검증 완료 전에는 태그 연결을 추가·제거·복원하지 않는다. 소유권 실패 로그에는 엔트리 ID와 콘텐츠 타입만 남기고 제목·본문·태그명은 기록하지 않는다.

### 멱등성

추가 요청에서 이미 연결된 태그와 제거 요청에서 이미 연결되지 않은 태그는 오류로 처리하지 않고 변경 없는 성공으로 다룬다. 활성 연결 중복 방지와 소프트 삭제 연결 복원 방식은 데이터 불변식 결정에 따라 구체화한다.

## 일회성 Undo 방향

- Undo 대상은 같은 검색 화면 세션에서 마지막으로 성공한 일괄 태그 작업 1건이다.
- Undo는 원래 요청 전체가 아니라 서버가 응답한 **실제 변경 연결 쌍**만 역연산한다.
- 추가 Undo는 해당 작업에서 새로 추가된 연결만 제거한다.
- 제거 Undo는 해당 작업에서 실제로 제거된 연결만 복원한다.
- 검색 결과 재조회, 검색 조건·정렬 변경, 엔트리 선택 변경은 Undo 상태를 지우지 않는다.
- 다음 일괄 추가·제거 또는 개별 엔트리·태그 쓰기 작업이 성공하면 이전 Undo를 폐기한다.
- 검색 화면을 벗어나거나 브라우저를 새로고침하면 Undo를 폐기한다.
- Undo 성공 후 현재 검색 조건으로 결과를 다시 조회하고 Undo 상태를 제거한다.
- Undo 실패는 현재 결과와 Undo 상태를 보존하고 오류를 표시해 재시도 가능하게 한다.
- Undo 상태는 검색 화면 메모리에만 둔다. 서버 작업 이력 테이블, `localStorage`, URL query에는 저장하지 않는다.

## 열린 질문

### 1. 선택 범위와 상한

- 개별 선택만 제공할지
- 현재 검색 결과 전체 선택을 제공할지
- 전체 선택을 제공한다면 결과 건수 상한을 얼마로 둘지
- 상한을 넘으면 전체 선택을 막을지, 검색 조건을 더 좁히도록 안내할지

검색 API가 현재 결과 전체를 반환하므로 query만 전달해 서버에서 숨은 대상을 다시 계산하는 방식과 클라이언트가 선택한 ID를 전달하는 방식은 구분해야 한다. 현재 아이디어는 사용자가 선택한 엔트리를 대상으로 가정하며, 검색 query만으로 대상을 재구성하는 방식은 별도 후보로 구분한다.

### 2. 완결 축과 선택 가능 여부

- 쓰기 잠긴 엔트리의 체크박스를 처음부터 비활성화할지
- 선택은 허용하되 적용 시 전체 요청을 거부할지
- 선택 집합에 쓰기 불가 엔트리가 섞이면 전체 롤백할지, 가능한 엔트리만 처리할지

현재 엔트리 수정은 일자 축별 완결 정책의 영향을 받으므로 일괄 태그도 같은 서버 경계를 우회할 수 없다.

### 3. 원자성과 부분 성공

- 요청 전체를 한 트랜잭션으로 처리하는 전체 성공/전체 실패
- 엔트리별 성공·실패를 반환하는 부분 성공

부분 성공은 재시도와 결과 설명이 복잡해지고, 전체 롤백은 하나의 잘못된 엔트리 때문에 정상 대상도 변경되지 않는다. 사용자 기대와 최대 처리 건수를 함께 보고 결정한다.

### 4. 태그 연결 데이터 불변식

- 활성 연결만 유일하게 할지, 소프트 삭제 이력을 포함해 연결 한 쌍당 행 하나만 허용할지
- 중복 행 중 어떤 행을 정본으로 남길지
- 삭제된 동일 연결을 복원할지 새 연결을 만들지
- 현재 JPQL hard delete와 entity soft delete를 어느 정책으로 수렴할지
- `ref_content_type`이 비어 있는 행의 출처와 처리 방식

이 결정은 일괄 기능뿐 아니라 현재 단건 태그 저장의 멱등성에도 영향을 준다. 데이터 정리와 제약 추가가 필요하면 UI/API 구현과 분리된 선행 SAVEPOINT로 다룬다.

### 5. 태그 선택 UI

- 검색 고급 필터의 기존 태그 자동완성 흐름을 재사용할지
- 일괄 작업 전용 모달을 둘지
- 선택 태그별 카테고리를 어떻게 표시할지
- 적용 전 예상 연결 수를 현재 결과 DTO에서 계산할지, 서버 preview를 둘지

신규 태그 생성은 현재 아이디어 범위 밖이므로 선택 UI는 기존 태그 ID를 확정해서 전송하는 방향을 가정한다.

### 6. 캐시와 비동기 후처리

- 영향받은 연·월을 모아 기간 캐시를 한 번씩 무효화하는 일괄 worker 형태
- 엔트리 상세 캐시의 ID별 무효화 범위
- 사용자·콘텐츠 타입 전체 태그 캐시의 중복 무효화 방지
- 변경된 엔트리만 엔티티 추출·임베딩 큐에 넣는 방식
- 큐 등록 실패를 태그 연결 트랜잭션 실패로 볼지, 커밋 후 재처리 가능한 오류로 남길지

단건 태그 처리 서비스를 엔트리 수만큼 반복 호출하는 구현은 같은 사용자 캐시를 반복해서 비우므로 일괄 처리 경로의 기준안으로 삼지 않는다.

### 7. 감사 로그와 이력

- 일괄 작업 요약 로그만 남길지
- 엔트리별 이력 스냅샷을 생성할지

일회성 Undo는 화면 메모리의 실제 변경분으로 처리하며, 영속 감사 로그와 엔트리 이력 정책은 별도로 결정한다.

## 구체화 단계 후보

구현에 진입할 경우 다음 분할을 검토한다. 이 순서는 아직 확정된 실행 계획이 아니다.

1. 기능 경계와 열린 질문을 합의하고 관련 spec에 `❌`로 등재
2. `tag_content` 데이터 불변식 조사·정리와 멱등 저장 기반
3. 일괄 추가·제거·Undo API, 소유권·완결 검증, 캐시·임베딩 후처리
4. 검색 화면 선택 UI, 추가·제거 확인, 일회성 Undo와 결과 재조회
5. 구현 상태에 맞춰 화면·인터랙션·저널 컴포넌트 spec을 `⚠` 또는 `✓`로 갱신

각 단계는 독립 SAVEPOINT에서 빌드·인코딩·호출 그래프 정합을 만족해야 한다.
