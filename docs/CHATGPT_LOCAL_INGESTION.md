# ChatGPT 대화 로컬 적재 작업 계약

## 1. 명령 해석

사용자가 **ChatGPT 대화 링크와 함께 `적재해`, `로컬에 적재해`, `파일로 적재해`처럼 적재 의사를 명시하면**, 해당 요청은 아래 정형 작업 전체에 대한 실행 승인이다.

- 현재 Codex 앱이 접근할 수 있는 ChatGPT 대화를 읽는다.
- 차단 조건이 발견되지 않은 대화의 현재 선택 흐름을 최초 턴부터 최신 턴까지 모두 조회한다. 차단 조건을 발견한 대화는 해당 페이지에서 조회를 종료한다.
- `daily/text/daily/YYYY/MM/DD/`의 기존 파일을 갱신하거나 새 텍스트 파일을 생성한다.
- `daily/text/daily/CHATGPT_INDEX.json`에 원격 수정 시각과 로컬 스냅샷 해시를 동기화한다.
- 조회 결과에 읽을 수 있는 로컬 경로가 제공된 `.txt` 및 이미지(`.png`, `.jpg`, `.jpeg`, `.webp`, `.gif`) 첨부파일을 대화 파일 옆에 보존한다.
- 턴 시작 시각을 발화자 태그에 포함한다.
- 아래 검증 절차까지 완료한다.

이 정형 작업에는 `AGENTS.md`의 일반적인 수정 직전 승인 질문을 다시 적용하지 않는다. 링크나 적재 의사가 없거나 대상 대화·저장 위치를 하나로 확정할 수 없는 경우에만 질문한다.

## 2. 대화 식별과 기본 저장 위치

1. URL의 `/c/{conversationId}`에서 대화 ID를 추출한다.
2. 링크 문자열이 중복되거나 Markdown 표시 URL과 대상 URL이 다르면 유효한 단일 ChatGPT 대화 URL로 정규화한다.
3. `daily/text/daily/CHATGPT_BLOCKED.md`에서 대화 ID의 상태를 먼저 확인한다.
4. `BLOCKED` 상태인 대화는 ChatGPT를 조회하지 않고 즉시 중단하여 등록된 차단 원인을 보고한다. 사용자가 `강제 재검증`, `차단 해제`, `우회로 적용`, `차단 메시지 복구`처럼 재조사나 수동 결합 준비를 명시한 경우에만 조회를 재개한다.
5. `ATTACHMENT_BLOCKED` 상태는 본문 조회를 중단하지 않는다. 일반 적재 요청에서도 대화와 기본 범위의 첨부파일을 다시 조회하여 자동으로 재검증한다.
6. `daily/text/daily/` 아래의 `YYYY/MM/DD/` 디렉터리에서 파일명 끝의 `__{conversationId}.txt`가 일치하는 기존 파일을 찾는다.
7. 기존 파일이 있으면 같은 대화의 로컬 스냅샷으로 간주하여 그 파일을 갱신한다.
8. 전체 조회에서 가장 오래된 턴의 `startedAt`을 `Asia/Seoul`로 변환하고 `YYYY/MM/DD` 형식의 저장 디렉터리와 `yyMMdd` 형식의 대화 시작일자를 결정한다.
9. 기존 파일이 없으면 ChatGPT가 제공한 현재 제목을 파일명에 안전하게 반영하여 `daily/text/daily/${YYYY}/${MM}/${DD}/${yyMMdd}_chatGPT_${제목}__${conversationId}.txt`로 저장한다.
10. 동일한 대화 ID의 기존 파일에서 저장 디렉터리 또는 시작일자 접두사가 현재 조회 결과와 다르면 `daily/text/daily/${YYYY}/${MM}/${DD}/${yyMMdd}_chatGPT_`가 일치하는 경로로 이름을 변경한다.
11. 제목이 바뀌어도 동일한 대화 ID의 기존 파일에서 제목 부분은 유지한다. 대화 ID가 다른 파일을 덮어쓰지 않는다.
12. 기본 범위의 첨부파일은 대화 파일의 `.txt` 확장자를 제외한 경로에 `.attachments`를 붙인 `${대화파일기본명}.attachments/` 디렉터리에 저장한다.
13. 첨부파일명은 조회 순서의 1부터 시작하는 세 자리 번호와 확장자를 포함해 안전하게 정규화한 원본 파일명을 결합한 `001_${원본파일명}` 형식을 사용한다. 절대경로, 상위 디렉터리 이동, 경로 구분자와 운영체제 금지 문자는 파일명으로 반영하지 않는다.

## 2.1. 변경 감지 인덱스

- `daily/text/daily/CHATGPT_INDEX.json`은 정상 적재된 ChatGPT 대화의 변경 감지 기준선이다.
- 각 항목은 `conversationId`, `remoteUpdatedAt`, `ingestedAt`, `contentSha256`, `file`을 기록한다. `remoteUpdatedAt`은 대화 목록 또는 본문 조회가 반환한 숫자 값을 그대로 보존하고, `contentSha256`은 저장한 본문 파일 원본 바이트의 SHA-256이다.
- 목록에 나타난 대화 ID가 로컬에 없으면 본문을 조회하여 새로 적재한다.
- 로컬 파일과 인덱스 항목이 모두 있고 목록의 `updatedAt`이 `remoteUpdatedAt`과 같으면 해당 대화의 본문 조회를 생략한다.
- 두 값이 다르거나 인덱스 항목·로컬 파일 중 하나가 없으면 전체 본문을 다시 조회하고, 정상 적재가 끝난 뒤 인덱스를 갱신한다.
- 사용자가 특정 대화의 내용 변경 가능성을 알리거나 강제 갱신을 요청하면 `updatedAt` 일치 여부와 관계없이 전체 본문을 다시 조회한다.
- 기존 로컬 파일에 최초 기준선을 도입할 때 현재 목록의 `updatedAt`을 본문 재조회 없이 등록할 수 있다. 이 기준선은 등록 이후의 값 변화만 감지하며 등록 이전의 본문 변경을 증명하지 않는다.
- 목록에 나타나지 않은 기존 로컬 파일은 인덱스 생성만을 위해 본문을 조회하지 않는다. 이후 목록에 나타나거나 사용자가 링크를 제공했을 때 기준선을 만든다.
- `BLOCKED` 대화, `*.partial.txt` 초안과 본문 조회가 완료되지 않은 대화는 정상 적재 인덱스에 추가하거나 기존 기준선을 갱신하지 않는다.
- 인덱스는 대화 ID 오름차순으로 정렬하고 UTF-8 BOM 없이 저장한다.
## 3. 원문 조회 계약

- Codex 앱의 ChatGPT 대화 조회 경로를 사용한다.
- 각 페이지를 받은 직후 차단 조건을 먼저 검사한다. 차단 조건이 없을 때만 `page.nextCursor`를 따라 다음 페이지를 조회하며, 정상 적재 후보는 `page.hasMore`가 `false`가 될 때까지 모든 페이지를 조회한다.
- 개별 메시지의 20,000자 상한 도달, 지원되지 않는 메시지 항목·텍스트 블록처럼 원문 완전성을 보장할 수 없는 조건을 하나라도 발견하면 해당 페이지에서 즉시 조회를 종료한다. 반환된 `nextCursor`와 이후 페이지는 조회하지 않는다.
- 응답 순서가 `newest_first`이면 전체 턴을 뒤집어 최초 턴부터 최신 턴 순서로 저장한다.
- 턴 ID가 중복되거나 페이지 커서가 끊기면 적재를 중단한다.
- 메시지별 조회 한도에 닿거나 잘림 징후가 있으면 완전한 원문으로 간주하지 않고 적재를 중단한다.
- 현재 선택된 대화 흐름만 적재한다. 대체 응답이나 다른 분기까지 가져왔다고 추정하지 않는다.
- 사용자와 Assistant의 텍스트는 요약·교정·번역·이스케이프하지 않고 반환된 문자열 그대로 보존한다.
- Assistant 응답이 없는 사용자 단독 턴은 사용자가 응답 전에 생성을 중지하거나 대화를 떠난 정상 원문일 수 있으므로 BLOCKED로 판정하지 않고 사용자 메시지만 저장한다. Assistant 텍스트가 일부라도 반환됐으면 반환된 부분만 저장하며 누락된 응답을 추정하지 않는다.
- 지원되지 않는 메시지 항목이나 텍스트 블록 유형이 나타나면 조용히 생략하지 않고 중단하여 보고한다.

### 3.1. 개별 메시지 조회 상한 판정

- 현재 ChatGPT 대화 조회 호출은 `maxOutputCharsPerItem=20000`으로 실행한다. 이 값은 대화 전체나 턴 전체가 아니라 각 `userMessage`·`agentMessage` 항목 하나에 적용되는 반환 상한이다.
- 대화 전체의 글자 수와 메시지 개수는 이 상한 판정에 영향을 주지 않는다. 여러 짧은 메시지의 합계가 20,000자를 넘어도 각 메시지가 상한에 닿지 않으면 차단 사유가 아니다.
- `userMessage`는 해당 항목의 텍스트 블록을 반환 순서대로 이어 붙인 문자열 길이, `agentMessage`는 해당 항목의 `text` 문자열 길이로 판정한다.
- 반환 문자열이 정확히 20,000자이면 원문이 정확히 20,000자인지, 더 긴 원문이 20,000자에서 잘렸는지 현재 응답만으로 구별할 수 없다. 따라서 “원문이 20,000자를 초과했다”고 단정하지 않고 “개별 메시지가 반환 상한에 도달하여 잘림 가능성을 배제할 수 없다”고 기록한다.
- 현재 응답에는 메시지의 원문 총길이·잘림 플래그·문자 offset·suffix 조회 옵션이 없다. `page.nextCursor`는 턴 사이를 이동하며 같은 메시지의 20,000자 이후 내용을 반환하지 않는다.
- 정확히 20,000자인 메시지 또는 그 밖의 잘림 징후가 하나라도 있으면 원문 완전성을 입증할 수 없는 `BLOCKED` 상태로 판정하고 불완전한 로컬 스냅샷을 만들지 않는다.
- 최초 상한 도달 메시지를 발견한 페이지에서 차단 판정을 확정하고 조회를 종료한다. 같은 페이지의 나머지 반환 항목은 추가 차단 사유를 찾기 위해 분석하지 않으며, 다음 페이지에 있을 수 있는 다른 상한 도달 메시지의 수와 위치도 수집하지 않는다.
- 동일한 긴 메시지를 대화의 마지막 턴으로 옮기거나 내용 변경 없이 분기해도 개별 메시지 상한은 유지되므로 해결책으로 간주하지 않는다.

### 3.2. 차단 메시지 식별 기록

- 차단 판정 시 `daily/text/daily/CHATGPT_BLOCKED.md`에 대화 ID, 제목, 발견일, 상태, 최초 차단 원인, 화면 식별 문구와 로컬 스냅샷 미생성을 기록한다.
- 차단 기록에는 조회 응답의 `thread.createdAt` 원본 숫자와 이를 `Asia/Seoul`의 `YYYY-MM-DD HH:mm:ss[.fraction]`으로 변환한 대화 시작일시를 함께 기록한다. 이 값은 차단 발견일이나 최초 차단 턴 시각과 구분한다.
- 기존 차단 기록의 시작일시를 소급할 때는 대화 본문을 저장하지 않는 최소 조회로 `thread.createdAt`만 확인할 수 있다. 대화가 현재 조회 경로에서 사라졌으면 시작일을 추정하지 않고 `조회 불가`와 실패 원인을 기록한다.
- 화면 식별 문구는 최초 차단 항목 하나만 기록한다. 상한 도달 메시지는 역할과 반환 접두부의 첫 120~180자를 사용한다.
- 사용자 메시지가 짧거나 중복되어 단독 식별이 어려울 때만 같은 조회 페이지 안의 인접 사용자·Assistant 문답 시작 부분을 보충한다.
- 차단 레지스트리에는 전체 페이지·턴 범위, 전체 차단 항목 수, 턴·메시지 순번, 턴·메시지 ID, 반환 문자열 길이, SHA-256과 첨부파일 현황을 추가로 계산·분석하거나 기록하지 않는다.
- 조기 종료 시점의 `hasMore=true`는 차단 결과이며 추가 조회 사유가 아니다.
- 사용자에게 차단 원인을 보고할 때도 UUID만 제시하지 않고 위 화면 식별 문구를 먼저 제시한다.
- 식별용 시작 부분은 반환된 접두부일 뿐 완전한 메시지나 원문 끝부분이 아니다.
- 차단 레지스트리는 개인 대화 식별정보와 짧은 원문 일부를 포함하므로 private `daily` 저장소에서만 관리한다. 메인 계약에는 실제 대화 제목이나 원문을 기록하지 않는다.

### 3.3. 사용자 조치와 재검증

- 원래 대화의 원문을 그대로 보존하려면 다음 경로를 사용한다.
  1. ChatGPT의 공식 데이터 내보내기로 전체 대화 데이터를 내려받는다.
  2. 압축을 푼 로컬 내보내기 파일 경로와 차단된 대화 ID를 제시하고 `우회로 적용` 또는 `강제 재검증`을 요청한다.
  3. 대상 대화 ID를 우선 대조하고, 공식 내보내기 안에서 레지스트리의 반환 접두부로 차단 메시지를 식별한다.
  4. 차단 메시지의 전체 원문과 나머지 턴을 모두 검증한 뒤 스냅샷을 만들고 상태를 `RESOLVED`로 전환한다.
- 공식 내보내기 재검증 요청은 사용자가 지정한 로컬 파일에서 대상 대화만 읽는 작업을 승인한다. 다른 대화는 저장하거나 별도 보고서·임시 파일로 복제하지 않는다.
- 메시지 내부 offset·suffix 또는 전체 항목 조회를 지원하는 검증된 조회 경로가 제공되면 같은 대화 ID로 `강제 재검증`을 요청할 수 있다.
- 긴 메시지를 18,000자 이하의 여러 메시지로 나눈 새 대화를 만들고 새 링크를 적재하면 개별 상한을 피할 수 있다. 다만 턴 구조와 Assistant 응답이 달라지므로 원래 대화의 차단 상태를 해제하지 않는다.
- 기존 긴 메시지를 18,000자 이하로 편집한 뒤 재조회하면 현재 선택 흐름은 적재할 수 있지만 편집 전 원문은 보존되지 않는다. 원래 대화 기록의 복원이 목적이면 공식 내보내기 또는 전체 항목 조회 경로를 사용한다.
- 우회 경로가 검증되거나 사용자가 재조사를 명시하면 해당 항목을 재검증한다. 전체 원문 적재와 완료 검증이 끝난 경우에만 `RESOLVED`로 전환한다.

### 3.4. 사용자 승인 수동 원문

- 사용자가 직접 확보한 텍스트 파일의 파일명에 정확한 대화 ID를 포함하고 `{conversationId} 수동 원문 승인`을 명시하면, 해당 파일을 그 대화의 완전한 원문으로 인정하여 정식 적재할 수 있다.
- 수동 원문 승인은 파일 내용의 완전성과 파일 안에 존재하는 리터럴 대체 문자 `�`를 포함한 모든 문자가 원문 그대로라는 사용자 확인이다. 승인받지 않은 수동 파일은 정상 적재 인덱스에 편입하지 않는다.
- `daily/text/daily/` 아래에서 파일명에 대상 대화 ID가 포함된 `.txt` 파일을 찾는다. 후보가 하나일 때만 사용하고, 없거나 둘 이상이면 대상 파일을 확정할 수 없으므로 중단한다.
- 차단 레지스트리의 대화 시작일시와 제목을 사용하여 파일을 `${YYYY}/${MM}/${DD}/${yyMMdd}_chatGPT_${제목}__${conversationId}.txt` 형식으로 정규화한다. 현재 목록에서 확인한 제목보다 차단 레지스트리에 기록된 제목을 우선하여 기존 식별 정보를 보존한다.
- 파일을 UTF-8로 엄격하게 디코딩할 수 있고 BOM이 없음을 확인한 뒤 원본 바이트의 SHA-256을 계산한다. 수동 승인 원문은 원격 조회 결과와 메시지 수·턴 시각·발화자 태그를 대조할 수 없으므로 해당 검증 항목 대신 사용자 승인을 완전성 근거로 기록한다.
- 현재 대화 목록에서 같은 ID를 확인할 수 있으면 그 `updatedAt`을 `remoteUpdatedAt` 기준선으로 등록한다. 목록에서 확인할 수 없으면 변경 감지 기준선을 확정할 수 없으므로 인덱스 편입을 중단한다.
- 정상 편입 후 차단 상태를 `MANUALLY_RESOLVED`로 전환하고 수동 승인일, 정규화된 로컬 스냅샷 경로와 완전성 근거를 기록한다. 최초 차단 원인과 식별 정보는 보존한다.
- `MANUALLY_RESOLVED`는 정상 적재 인덱스에 포함되는 해결 상태다. 이후 목록의 `updatedAt`이 기준선과 같으면 본문 조회를 생략하고, 값이 달라지면 일반 변경 감지 절차로 재조회한다. 재조회가 다시 차단되면 기존 수동 스냅샷과 인덱스 기준선은 보존하고 상태를 `BLOCKED`로 되돌려 새 차단 사실을 기록한다.

### 3.5. 상한 도달 메시지 부분 수동 복구

- 사용자가 차단된 대화 ID 또는 현재 목록의 차단 대화 전체와 함께 `차단 메시지 복구`, `2만자 메시지 표시`, `차단 대화 다 적재`, `결합`처럼 부분 수동 복구 의사를 명시하면, 일반 적재의 최초 차단 즉시 종료 규칙 대신 이 절의 복구 조회를 적용한다.
- 복구 조회는 `page.hasMore=false`가 될 때까지 현재 선택 흐름의 모든 페이지를 읽고, 턴 ID 고유성과 숫자형 `startedAt`을 검증하며, 반환 문자열이 정확히 20,000자인 모든 사용자·Assistant 메시지를 시간순으로 수집한다. 20,000자를 초과했다고 단정하지 않고 반환 상한 도달 메시지로 기록한다.
- 상한에 닿지 않은 메시지는 표준 스냅샷 형식으로 보존한다. 각 상한 도달 메시지는 시간순으로 `blocked-001`부터 번호를 부여하고 반환된 20,000자를 다음 마커 사이에 그대로 둔다.

```text
<<<CHATGPT_BLOCKED_MESSAGE_BEGIN blocked-001 role=user returnedChars=20000>>>
반환된 20,000자
<<<CHATGPT_BLOCKED_MESSAGE_END blocked-001>>>
```

- 부분 스냅샷은 표준 파일명의 마지막 `.txt`를 `.partial.txt`로 바꾼 경로에 UTF-8 BOM 없이 저장한다. 같은 대화의 기존 부분 스냅샷은 전체 원격 흐름을 다시 조회하여 교체하며, 정식 `.txt`와 `CHATGPT_INDEX.json`은 변경하지 않는다.
- 부분 스냅샷을 저장한 뒤에도 상태는 `BLOCKED`로 유지한다. 차단 레지스트리에 부분 스냅샷 경로, 전체 상한 도달 메시지 수와 각 번호의 역할·턴 위치·`startedAt`·반환 접두부 첫 120~180자를 기록한다.
- 사용자는 각 `BEGIN`과 대응 `END` 마커 사이의 반환 문자열을 해당 메시지의 전체 원문으로 교체하고 두 마커는 그대로 보존한다.
- 사용자가 `{conversationId} 결합 승인` 또는 `{conversationId} 차단 메시지 결합 승인`을 명시하면 마커 사이 내용의 완전성과 리터럴 대체 문자 `�`를 포함한 모든 문자가 원문 그대로라는 확인으로 간주한다. 부분 스냅샷은 UTF-8로 엄격하게 디코딩되고 BOM이 없으며 번호별 시작·종료 마커가 각각 하나여야 한다.
- 각 마커 사이 수동 메시지의 첫 20,000자는 대응하는 최신 원격 반환 문자열 전체와 정확히 일치해야 한다. 상한 도달 메시지 전부에 대해 접두부 일치가 확인되어야 하며, 하나라도 없거나 불일치하면 승격하지 않고 `BLOCKED` 상태와 부분 스냅샷을 유지한다.
- 검증에 성공하면 시작·종료 마커만 제거하여 표준 `.txt` 스냅샷으로 승격하고 `.partial.txt`를 제거한다. 첨부파일은 5절의 일반 규칙으로 보존한다.
- 정상 적재 파일과 인덱스 검증을 마친 뒤 차단 상태를 `MANUALLY_RESOLVED`로 전환하고 승인일, 스냅샷 경로, 전체 상한 도달 메시지 수와 각 대응 번호의 접두부 검증 완료를 기록한다. 최초 차단 원인과 식별 정보는 보존한다.
- 결합 시점의 전체 원격 흐름은 다시 조회하여 사용자가 원문을 준비한 사이 생긴 변경을 반영한다. 상한 도달 메시지의 수·순서·접두부가 준비 조회와 달라졌으면 기존 승인 파일을 임의로 대응시키지 않고 새 식별 목록을 보고한다.

## 4. 시간과 발화자 형식

- 각 턴의 `startedAt`을 해당 턴의 사용자 및 Assistant 발화 태그에 함께 기록한다.
- 시간대는 `Asia/Seoul`을 사용한다.
- 표기 형식은 `YYYY-MM-DD HH:mm`이며 초와 밀리초를 기록하지 않는다.
- Assistant 태그의 시간도 Assistant 생성 시작·완료 시각이 아니라 해당 턴의 `startedAt`이다.
- 저장 형식은 다음과 같다.

```text
<user 2026-01-02 09:30>
사용자 원문

<assistant 2026-01-02 09:30>
Assistant 원문
```

- 턴과 발화 사이는 빈 줄 하나로 구분한다.
- 대화 제목, 미리보기, 상태, 메시지 ID, 완료 시각, 페이지 커서는 기본 텍스트 파일에 추가하지 않는다.

## 5. 첨부파일과 스냅샷 범위

- 기본 적재 범위는 사용자와 Assistant의 텍스트 및 원본 파일명의 마지막 확장자가 대소문자 구분 없이 `.txt`, `.png`, `.jpg`, `.jpeg`, `.webp`, `.gif`인 첨부파일이다. 이미지는 텍스트 스크린샷·화면 상태·도표를 포함할 수 있으므로 일반 적재 요청에서도 보존한다.
- 기본 범위의 첨부파일은 조회 응답이 원본 파일명과 읽을 수 있는 로컬 파일 경로를 제공한 경우 자동으로 보존한다. 경로가 실제 일반 파일인지 확인하고, 저장 대상이 대화별 `.attachments` 디렉터리 내부인지 확인한 뒤 읽는다.
- 기본 범위의 첨부파일에는 별도 크기 상한을 두지 않는다. 조회 또는 로컬 파일 읽기가 실패하면 원문을 추정하거나 부분 파일을 만들지 않는다.
- 첨부파일은 원본 바이트를 그대로 복사하며 문자 인코딩, 줄바꿈, BOM과 파일 내용을 변환하지 않는다.
- 동일한 대상 파일이 이미 있고 SHA-256이 같으면 기존 파일을 재사용한다. 이름은 같지만 바이트가 다르면 기존 파일을 덮어쓰거나 삭제하지 않고 새 파일명에 SHA-256 앞 8자를 붙여 함께 보존한다.
- 같은 대화를 다시 적재해도 기존 첨부파일을 자동 삭제하지 않는다. 현재 조회에서 다시 확인된 첨부파일만 검증 결과에 포함한다.
- 기본 이미지 확장자 이외의 이미지 형식과 `.txt`·기본 이미지가 아닌 기타 첨부파일은 사용자가 첨부 적재까지 요청한 경우에만 별도로 보존한다. 이미지는 OCR·내용 해석·변환·압축 없이 원본 바이트 그대로 보존한다.
- 일반 적재에서 대화 본문이 `BLOCKED`로 판정되면 첨부파일 메타데이터가 같은 페이지에 반환됐더라도 첨부파일을 읽거나 저장하지 않고 즉시 종료한다. 3.5절의 부분 수동 복구에서는 전체 조회에서 확인된 기본 범위의 첨부파일을 부분 스냅샷과 함께 보존한다.
- 텍스트가 없는 첨부 전용 발화는 빈 발화자 블록을 남겨 턴의 위치를 보존한다.
- 기본 범위의 첨부파일 메타데이터가 있지만 읽을 수 있는 경로가 없거나 원본 파일을 읽지 못하면, 검증된 대화 본문은 정상 저장하고 `daily/text/daily/CHATGPT_BLOCKED.md`에 `ATTACHMENT_BLOCKED`로 기록한다.
- `ATTACHMENT_BLOCKED` 기록에는 대화 ID, 제목, 발견일, 사용자에게 보이는 관련 발화 문구, 원본 첨부파일명, 실패 단계와 원인, 본문 저장 경로, 재검증 방법을 기록한다. 발화와 첨부파일의 연결 관계가 응답에 없으면 관계를 추정하지 않고 “연결 정보 미제공”으로 명시한다.
- 사용자가 직접 내려받은 기본 범위의 로컬 첨부파일 경로와 함께 `첨부 재검증`을 요청하면 해당 파일을 누락 첨부의 권위 있는 대체 원본으로 읽어 보존할 수 있다. 지정받지 않은 다른 로컬 파일은 읽지 않는다.
- 누락된 모든 기본 범위의 첨부파일이 원본 바이트로 저장되고 검증되면 해당 항목을 `RESOLVED`로 전환한다.
- 결과 파일은 조회 시점의 스냅샷이다. 이후 ChatGPT 대화 변경을 자동 동기화하지 않는다.
- 같은 대화 링크를 다시 적재하면 원격 현재 흐름 전체를 다시 조회하여 기존 스냅샷을 교체한다.

## 6. ChatGPT에서 허용되는 동작

적재는 **읽기 전용 수집**이다. ChatGPT에는 조회 외 상태 변화를 남기지 않는다.

허용:

- 대화와 턴 조회
- 텍스트, 기본 범위의 `.txt`·이미지 첨부파일 및 사용자가 별도로 요청한 첨부파일 읽기
- 대화 제목과 식별 메타데이터 조회

금지:

- 대화에 메시지 전송
- 대화 제목·프로젝트·고정·보관 상태 변경
- 대화 삭제·공유·분기
- ChatGPT 상태 변경을 동반하는 기타 작업

## 7. 사용하지 않는 우회 경로

- ChatGPT 대화 조회 경로가 접근할 수 없으면 브라우저 스크래핑으로 우회하지 않는다.
- 브라우저 쿠키·로컬 저장소·세션 저장소를 읽지 않는다.
- 로컬 DreamDiary API나 DB에 원문을 저장하지 않는다.
- 원문 전달용 임시 파일, 변환 스크립트, 별도 보고서를 만들지 않는다.
- 누락된 시간이나 메시지 내용을 추정하여 채우지 않는다.

## 8. 완료 검증과 보고

1. 정상 적재는 마지막 페이지까지 조회했고 `hasMore`가 `false`인지 확인한다. `BLOCKED` 조기 종료는 최초 차단 조건이 나온 페이지 뒤로 조회하지 않았는지 확인한다. 상한 도달 메시지 부분 수동 복구는 마지막 페이지까지 조회하고 모든 상한 도달 메시지를 시간순으로 식별했는지 확인한다.
   본문 `BLOCKED` 조기 종료에는 아래 2~7의 스냅샷·첨부파일 검증을 적용하지 않는다.
2. 전체 턴 ID가 고유하고 모든 턴에 숫자형 `startedAt`이 있는지 확인한다.
3. 조회한 사용자·Assistant 메시지 수와 파일의 발화자 태그 수가 각각 일치하는지 확인한다.
4. 정상 적재 항목의 `contentSha256`이 저장 파일 원본 바이트의 SHA-256과 일치하고, `file`이 같은 대화 ID의 실제 파일을 가리키는지 확인한다.
5. 시간 태그와 차단 마커를 제거한 파일 본문이 조회 원문과 일치하는지 확인한다. 부분 수동 복구 초안에서는 마커 사이가 원격에서 반환된 20,000자와 일치하고 나머지 본문은 원격 조회 원문과 일치하는지 확인한다. 승인 승격에서는 각 마커 사이 전체 메시지의 첫 20,000자가 최신 원격 반환 문자열과 일치하는지 확인한다.
6. 대상 파일이 UTF-8 BOM 없음으로 엄격하게 디코딩되는지 확인한다. 정상 원격 적재에는 대체 문자가 없음을 확인하고, 사용자 승인 원문은 승인 범위에 리터럴 대체 문자 `�`가 포함될 수 있다.
7. 현재 조회에서 확인된 기본 범위의 첨부파일마다 원본과 저장 파일의 바이트 길이 및 SHA-256이 일치하는지 확인한다.
8. 기본 범위의 첨부파일을 읽지 못했다면 본문 저장 성공과 별도로 `ATTACHMENT_BLOCKED` 기록이 생성되었는지 확인한다.
9. `git diff`로 대상 파일·첨부파일·계약 문서·`AGENTS.md` 외 변경을 만들지 않았는지 확인하고 한글이 보존됐는지 확인한다.
10. `python scripts/check_encoding.py`로 UTF-8 게이트를 확인한다. 첨부파일의 원본 바이트는 UTF-8 검사 대상으로 변환하지 않는다.
11. 자동으로 stage·commit·push하지 않는다.
12. 정상 적재 결과 보고에는 저장한 절대 경로, 턴·메시지 수, 시간 범위, 첨부파일 저장 결과와 검증 결과만 간결하게 남긴다. 일반 `BLOCKED` 결과는 제목, 최초 화면 식별 문구, 차단 원인과 스냅샷 미생성만 보고한다. 부분 수동 복구 결과는 부분 스냅샷 절대 경로와 상한 도달 메시지 번호·역할·위치·식별 접두부를 보고한다.
