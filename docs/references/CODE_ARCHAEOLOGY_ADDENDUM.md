# 소스코드 고고학 방법론 — 부록: 산출물 분리와 3층 사건 탐지

> 본 부록은 CODE_ARCHAEOLOGY_CHECKLIST 방법론의 확장이다.
> **스택·제품 비종속.** 특정 저장소의 수치·파일명·도메인명·통섭 문장·문서 링크는 본문에 두지 않는다 — 어느 저장소에나 그대로 이식되는 중립 규칙이다. 예시는 실물 대신 `<placeholder>`·`A→B` 같은 추상 형태로만 든다.

---

## 1. 산출물은 두 문서로 분리한다

고고학 조사의 산출물은 **정적분석 보고서**와 **역사서**로 나뉜다. 둘은 목적이 다르고 독자가 다르다. (파일명·위치는 각 저장소가 정한다 — 이 문서는 역할만 규정한다.)

### 정적분석 보고서

**질문**: "지금 이 코드의 구조적 상태는 어떤가?"

**내용**: PRESSURE 표(파일별 크기·churn·fan-in·co-change·위험도) · Dead/Zombie 목록 · TODO/FIXME 현황 · 성장곡선(연도별 LOC/파일 수) · co-change 상위 쌍 · fan-in 허브.

**성격**: 현재 스냅샷의 상태 평가. 정량적. 릴리스 판단에 직접 사용.

### 역사서

**질문**: "이 코드는 어떤 사건들을 거쳐 지금의 모습이 되었는가?"

**내용**: 사건 연표(변곡점 중심) · 각 사건의 의미·영향·후속 · 시대 구분 · 통섭(이 코드베이스의 문명적 성격).

**성격**: 시간 축의 서사. 정성적. 설계 결정의 맥락을 제공.

### 관계

정적분석은 역사서의 **증거물**이고, 역사서는 정적분석의 **해석**이다. 둘 다 필요하지만 한 문서에 섞지 않는다.

## 2. 역사서 작성을 위한 3층 사건 탐지 프레임워크

역사서를 쓰려면 먼저 **사건을 식별**해야 한다. 사건 탐지에는 3개 층위가 필요하다.

### 1층: 물리적 변곡점 (자동)

**탐지 대상**: 대량 rename, 대량 delete, 대량 insert, 디렉토리 생성/소멸.

**방법**: `git log --shortstat` + `--diff-filter=R` 조합으로 각 커밋의 구조적 규모를 scoring.

**scoring 기준(예시 임계값 — 저장소 규모에 맞게 조정)**:
- 삭제 200줄 이상 → score += 삭제량/100
- 추가 500줄 이상 → score += 추가량/200
- rename 3건 이상 → score += rename수 × 2
- 파일 20개 이상 변경 → score += 파일수/5
- 총 churn 1000줄 이상 → score += churn/500

**강점**: 규모가 큰 거대 사건을 놓치지 않음.
**한계**: 규모는 작지만 방향을 바꾼 사건(설계 선회)을 놓침.

### 2층: 개념 탄생 (자동)

**탐지 대상**: 새 Entity/Service/Repository/Component 파일의 최초 출현.

**방법**: 현재 트리의 해당 스택 파일 목록(예: `*Entity.*`, `*Service.*`, 컴포넌트·스토어)을 추출한 뒤, 각 파일의 `git log --diff-filter=A --reverse -1`로 최초 커밋을 식별.

**의미**: 파일 하나의 탄생이 곧 **새 도메인 개념의 탄생**일 수 있다.
- `<외부통합>Service` 최초 출현 = 그 통합(예: LLM·결제·메시징)의 시작.
- `<핵심>Entity` 최초 출현 = 단일 테이블 상속(STI) 같은 도메인 모델 결정의 물증.

**강점**: 규모와 무관하게 "새 개념의 출현"을 잡음.
**한계**: rename에 의한 재생성과 진짜 탄생을 구분하려면 커밋 메시지 참조 필요.

### 3층: 설계 결정 (반자동)

**탐지 대상**: 커밋 메시지의 구조적/아키텍처적 결정 키워드.

**키워드 패턴**:
```
한국어: 수렴, 폐기, 제거, 삭제, 전환, 도입, 통합, 분리, 재편, 흡수, 걷어내기
영문:   remove, delete, merge, split, introduce, deprecate, replace, migrate, absorb, converge
패턴:   →, ->, 패키지.*변경, 구조.*변경
```

**방법**: `git log --format="%ad|%H|%s"` 전체를 키워드 매칭. 복수 키워드 매칭 시 고신뢰.

**강점**: 규모는 작지만 방향을 바꾼 결정을 잡음 — 문서 몇 줄짜리 "설계 확정" 커밋이 이후 모든 작업의 분기점인 경우.
**한계**: 키워드 없는 결정은 놓침. false positive 있음(단순 rename도 `→`로 걸림) — 에이전트 판단으로 필터링.

## 3. 사건 묶기 (4층 — 수동/에이전트 초안)

3개 층에서 추출한 개별 커밋을 **하나의 역사적 사건**으로 묶는다.

**원칙**:
- 같은 주(week) 안, 같은 목적의 연속 커밋 = 하나의 사건.
- "도입 → 폐기"가 24시간 이내면 "실험"이라는 단일 사건.
- rename + 이전 이름 삭제 = "이름 혁명" 하나.
- Phase 1/2/3… = "○○ 수렴"이라는 하나의 사건(각 phase는 sub-event).

**추상 예시**:
```
사건: 단명 실험 (도입일 ~ 익일)
  - Day N   : <개념> 도입 (+대량 줄, 다수 파일)
  - Day N+1 : <개념> 폐기, 다른 구조로 수렴 (−대량 줄)
  의미: 24시간 만에 대체 구조로 흡수된 시도.
```
```
사건: 대량 rename 혁명 (연속 며칠)
  - oldPrefixA → newPrefixA (수백 renames)
  - oldPrefixB → newPrefixB (수백 renames)
  의미: 이름의 혁명. 이후 git --follow 분석에 영구 영향(전후를 갈라 읽어야 함).
```

---

## 4. 작업 순서

```
1. 1층 스크립트 실행 → 물리적 변곡점 Top N 추출
2. 2층 스크립트 실행 → 핵심 개념 탄생 연표 추출
3. 3층 스크립트 실행 → 설계 결정 커밋 추출
4. 3개 층 결과를 시간순 병합
5. 사건 묶기(4층) — 관련 커밋을 역사적 사건으로 추상화
6. 역사서 초안 작성 (사건 → 영향 → 후속)
7. 정적분석 보고서 별도 작성 (현재 스냅샷 상태)
```

---

## 5. 증거 비용 참조

| 분석 | 비용 | 강도 | 비고 |
|------|------|------|------|
| 1층 shortstat scoring | ~1분 | 강 | 전체 히스토리 구조 변동 |
| 2층 concept birth | ~5분 (파일당 git log) | 중 | 새 도메인 개념 식별 |
| 3층 keyword match | ~30초 | 약~중 | false positive 있음, 에이전트 필터 필요 |
| 4층 사건 묶기 | ~30분 (수동) | 강 | 역사적 해석 |
| 정적분석 (churn/fan-in/co-change) | ~3분 | 강 | 현재 상태 평가 |

## 6. 과잉조사 중단 조건

역사서 작성은 아래 중 하나를 만족하면 중단한다:

- 주요 시대 구분이 확정되고, 각 시대의 대표 사건이 1개 이상 식별됨.
- 새 층위를 추가해도 기존 사건 목록이 바뀌지 않음(포화).
- 조사 비용이 역사서 가치를 초과(개인 프로젝트 기준: 4시간 이상이면 재고).

## 7. 보고서 서식 원칙 — PRESSURE 항목의 3단 분리

모든 PRESSURE 항목은 **Signal → Interpretation → Action**으로 분리한다. 증거(사실)·해석(판단)·권고(행동)를 한 줄에 섞지 않는다.

### 서식 (추상 예시)

```
Signal (확정된 사실)
  - 크기: 매우 큰 단일 파일 (LOC·바이트 수치)
  - fan-in: 소수 진입점에서만 호출
  - churn: 낮음
  - revert/hotfix: 0건

Interpretation [강한추정]
  - God Object — 한 파일에 여러 관심사(입력·분류·합성·검증·오케스트레이션) 혼재
  - 현재는 안정적이나, 다음 기능 추가 시 팽창 관성이 살아있음

Counter Evidence
  - churn 낮음 = 자주 안 건드림 = 현재 폭발 아님
  - 테스트 존재 + 1:1 co-change = 커버리지 있음
  - fan-in 낮음 = 외부 영향 범위 제한적

Time Horizon
  - 현재: 안정 (위험도 ⚪)
  - 확장 시: 높음 (위험도 🔴) — 새 관심사/축 추가 시

Action
  - 즉시: 없음
  - 중기: 분해 검토 (<관심사A>/<관심사B>/<관심사C>/Orchestrator 로 추출)
  - 근거: Signal의 "매우 큰 단일 파일" + "관심사 혼재" → 단일 변경의 영향 범위 예측 불가
```

### 원칙

- **Signal**에는 `[확정]`만. 수치·파일 목록·git 출력 등 검증 가능한 사실.
- **Interpretation**에는 반드시 Confidence 등급을 붙인다.
- **Counter Evidence**는 해석에 반대되는 증거를 명시한다("무조건 나쁜 건 아니다"를 읽는 사람이 이해하게).
- **Time Horizon**은 최소 2단계(현재 / 확장 시). 팀 프로젝트는 3단계(현재 / 6개월 / 확장 시).
- **Action**에는 "근거: Signal의 어떤 항목이 이 권고를 만들었는가"를 역참조한다.

## 8. Confidence 등급은 보고서에서도 유지한다

체크리스트(§0)의 증거 등급을 보고서 산출물에서도 그대로 쓴다.

```
[확정]       코드/Git/DB/설정/문서에서 직접 확인
[강한추정]   복수 정황을 일치시킨 추정 (반증 없음)
[미확인]     증거 부족, 아직 단정 불가
```

**적용 위치:**
- PRESSURE 표의 "응력 유형"(Interpretation) → 등급 필수.
- co-change 해석("독립 변경 불가능") → `[강한추정]`.
- Dead/Zombie 판정 → 빌드 미포함이면 `[확정]`, 사용 여부 미확인이면 `[강한추정]`.

## 9. "하지 말아야 할 것" 절

보고서 마지막에 반드시 포함한다. 구조적 위험의 존재가 즉시 행동으로 이어지는 오독을 방지한다.

### 서식 (추상 예시)

```
이번 조사에서 권장하지 않는 행동

- <대형 God 파일> 즉시 분해 — churn 낮고 장애 없음. 분해 비용 > 현재 리스크.
- <고 fan-in 공통 축> 대규모 리팩터 — 현재 안정. 확장 시에만 리스크 현실화.
- <미배선 평행 표면> 즉시 삭제 — 명시적 폐기 결정을 먼저 내린 뒤 삭제.
- <진행 중 재설계> 강행 — 병행 작업의 자연 지연을 사고로 분류하지 않음.

근거: "구조적으로 위험한 것"과 "지금 고쳐야 하는 것"은 다르다.
시한폭탄은 제거 계획을 세우되, 폭발하지 않는 한 당장 해체하지 않는다.
```

## 10. Counter Evidence 원칙

모든 "위험" 판정에는 반대 증거를 병기한다. 한쪽만 보여주는 보고서는 신뢰를 잃는다.

**의무 기재 조건**: PRESSURE 표에서 위험도 🟠 이상인 항목은 Counter Evidence 필수.

**추상 예시**:

| 항목 | 위험 해석 | 반대 증거 |
|------|-----------|-----------|
| 초대형 단일 서비스 | God Object | churn 낮음, 장애 0, 테스트 존재 |
| 두 컴포넌트 고빈도 co-change | 강결합 | 계층 관계상 자연스러운 면, 후속 리팩터 기회 있음 |
| enum/유틸 초고 fan-in | 허브 리스크 | 값 추가는 기존 코드 안 깨뜨림, 안정 축 |

---

## 11. 권고의 근거 역참조

모든 권고(Action)에는 "이 권고를 만든 증거"를 명시한다. 읽는 사람이 "왜?"를 물을 때 보고서 안에서 답을 찾을 수 있어야 한다.

### 서식 (추상 예시)

```
권고: <대형 God 파일> 중기 분해 검토
근거:
  - Signal: 매우 큰 단일 파일 (LOC/바이트) — PRESSURE 표
  - Signal: 여러 관심사 혼재 — 역사서 해당 장
  - Interpretation: 단일 변경의 영향 범위 예측 불가 [강한추정]
  - Counter: churn 낮음 → "즉시"가 아닌 "중기"로 판정
```

## 12. Time Horizon — 위험의 시간축

"위험하다"만으로는 불충분하다. **언제 위험한가**를 명시한다.

| 시간축 | 의미 | 행동 |
|--------|------|------|
| 현재 | 오늘 폭발 가능 | 릴리스 차단 or 즉시 대응 |
| 단기 (1~2 릴리스) | 다음 기능 추가 시 위험 | 계획에 포함 |
| 확장 시 | 규모/팀/요구 변경 시 위험 | 인지만. 트리거 조건 기록 |

**적용**: PRESSURE 표의 "위험도" 옆에 Time Horizon 칸 추가.

## 13. False Positive History

오판 사례를 기록한다. 같은 실수를 반복하지 않기 위해.

### 서식 (추상 예시)

```
False Positive Log

| 조사 | 초기 가설 | 결과 | 오판 원인 | 학습 |
|------|-----------|------|-----------|------|
| <날짜/저장소> | "legacy 잔존" | 이미 해소됨 | 삭제 이력(--diff-filter=D) 미확인 | 1층 분석 시 삭제 커밋도 함께 추출 |
```

- **위치**: 적용록 메타 절에 포함. 사례가 3건 이상 쌓이면 별도 문서로 분리(파일명은 저장소가 정함).
- **목적**: 다음 저장소에 적용할 때 "이전에 이런 착각을 했다"를 참조 가능.
