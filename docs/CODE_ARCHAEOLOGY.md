# 소스코드 고고학 방법론 — 산출물 분리, 3층 사건 탐지, 인간 층

> 이 문서가 소스코드 고고학 프로토콜의 정본이다.
> **스택·제품 비종속.** 특정 저장소의 수치·파일명·도메인명·통섭 문장·문서 링크는 본문에 두지 않는다 — 어느 저장소에나 그대로 이식되는 중립 규칙이다. 예시는 실물 대신 `<placeholder>`·`A→B` 같은 추상 형태로만 든다.

해석은 다섯 층으로 읽는다. 체감은 탐지 입력이고 scoring이 아니다. 인간 층은 **사건 묶기의 속성**이다.

```
체감 층  — 변경자가 이 구조를 어떻게 경험하는가 (가설 생성기)
코드 층  — 무엇이 변했는가
시간 층  — 언제 사건이 발생했는가
인과 층  — 왜 위험/변곡점인가
인간 층  — 누가 지식을 들고 들어오고 나갔는가
```

체감 층은 scoring이 아니다. 원초적 질문이다: **왜 이 코드를 건드릴 때마다 고통스러운가. 그 고통은 어떤 누적의 결과인가.** 증거론(기본 브랜치, 회고/Git 분리, salience, counter)은 헛소리를 줄인다. 체감 층을 지우면 측정치만 남고 진단이 없다.

`누가`는 평가(기여도·서열)가 아니다. **코드 소유권과 지식 이동의 증거**다.

## 목적 — 왜 파나

나쁜 코드를 찾아내는 방법론이 아니고, Git을 요약하는 방법론도 아니다.

**현재 개발자가 느끼는 변경 고통을 구조적 압력으로 분해하고, 그 압력이 어떤 역사적 누적으로 형성되었는지를 복원한다.** 동시에, 그 고통의 원인이 아닌 확정 변곡도 객체 일대기의 일부로 남긴다. 전자는 발굴의 초점이고, 후자는 역사의 존재론이다. 둘을 한 목적함수로 합치지 않는다.

판정 invariant는 셋이다. 이후 절의 금지·의무는 여기서 파생한다. 네 번째 축이 생겨도 국소 방어문을 쌓지 말고 이 표에 칸을 더한다.

| 판단 | 축 | 하는 일 | 하지 않는 일 |
|------|-----|---------|--------------|
| 보존 | 역사적 중요도 | 변곡이면 시대/사건으로 남긴다 | FIRST CONTACT가 설명하지 않는다고 지우기 |
| 현재 서사의 중심 | 인과적 중요도 | 핵·직접 원인·위계를 정한다 | 핵이 아닌 것을 비존재로 만들기 |
| 별도 문서 승격 | 서술 배율 | 상위 서사를 왜곡하면 객체 역사서로 분리한다 | 현재 고통을 설명해야만 승격하기 |

FIRST CONTACT는 조사 렌즈다. 구조/Git이 역사적 존재를 판정한다. 인과관계는 현재 질문에서의 위계다. 서술 배율은 산출물 배치다.

FIRST CONTACT는 **둘이**다. 서로 대체하지 않는다.

| | 현상 FIRST CONTACT | 변경 FIRST CONTACT |
|--|-------------------|-------------------|
| 물음 | 과제를 정하기 **전에** 이 객체를 열면, **무엇이 이해를 방해하는가?** | 규칙 하나를 바꾸려면 어디를 횡단하는가? |
| 잡는 것 | 객체 자체의 괴물(상태기계를 인간이 실행해야 함, 지원 세계 공백, 실행면 부재…) | 그 괴물 위의 **한 왕복** |
| 실패 | 변경 질문만 잡고 수행 화면·인터프리터를 렌즈 밖으로 밈 | 현상 충격(큰 파일)을 핵으로 씀 |

현상 쪽의 센서는 LOC가 아니다. **화면/객체의 가능한 행위(지금 상태, 왜 이 버튼, 다음은 무엇인가)를 문장으로 말할 수 있는가.** 못 하고 코드를 실행하듯 따라가야 하면, 그게 현상 FIRST CONTACT다. 변경 과제가 좋아도 이 방해를 「이웃」으로 밀어 조사를 끝내지 않는다.

출발점은 커밋 목록이 아니다. 객체를 처음 열었을 때의 이해 방해, 그리고 고치려고 열었을 때의 왕복이다. 현장이 달라도 충격의 구조는 다를 수 있다(지원 세계 공백 vs 정책이 분기에만 있음 vs 실행면 부재). 한 콤플렉스로 묶지 않는다. 충격이 없는 코드라면 이 작업을 하지 않는다.

그 충격을 결론으로 쓰지 않는다. 없애지도 않는다. 계기판이다. 「무엇 때문에」로 바꿔 코드·Git으로 죽인다. 산출물이 수치·SHA만 있고, 현상(행위가 왜 안 읽히는가)과 변경(어디를 고치는가) 중 **해당 조사의 렌즈**에 답하지 못하면 실패다.

큰 파일·복제·포크·우회는 보일 수 있다. 변경 비용의 핵은 종종 그 형태가 아니다. **코드에 하나의 representation으로 없는 개념을, 변경자가 연산마다 머릿속에서 재구성하는 비용**이다. 그 representation은 DB 표여야 한다는 처방이 아니다. 객체·전략·설정·스키마 무엇이든, 한곳에서 읽히면 된다. 진단은 「canonical이 없다 / 제어흐름에서 반복 재구성된다」까지다. 「표를 만들라」는 별 결정이다.

## 0. Git 기준 — 프로젝트 기본 브랜치만

고고학의 화석은 **그 저장소의 기본(마스터) 브랜치**다. 이름은 `main`이든 `master`든, 그 프로젝트가 정한 default다. 확인: `git symbolic-ref refs/remotes/origin/HEAD` 또는 저장소가 명시한 기본 브랜치. 그 이름이 바뀌어도 규칙은 같다 — **기본 브랜치**.

다음으로 화석을 읽지 않는다. 나온 문장은 **버린다.** 각주·「참고」·「현재 브랜치에는」으로 남기지 않는다.

| 금지 | 이유 |
|------|------|
| 워킹트리·인덱스·미커밋 파일 | 아직 역사가 아님 |
| 현재 checkout (`HEAD`) | 작업 브랜치를 가리킬 수 있음 |
| feature / test / 로컬 실험 브랜치 | 착지하지 않은 작업 |
| `git ls-files`, 에디터, 디스크 glob | 기본 브랜치에 없는 경로가 보임 |

허용하는 읽기만:

```
git show <default>:<path>
git log <default> -- <path>
git ls-tree -r --name-only <default> -- <dir>
git cat-file -e <default>:<path>    # 경로를 쓰기 전 필수
git merge-base --is-ancestor <sha> <default>    # 커밋을 쓰기 전
```

경로·파일명·blob 비교·테스트 개수·「세 파일이 공존」은 위가 통과한 뒤에만 `[확정]`. 통과 못 하면 그 문장은 고고학이 아니다.

정적분석의 “현재 스냅샷”도 **기본 브랜치 트리**다. 체크아웃된 작업 복사가 아니다.

산출물 첫머리에 기본 브랜치 이름과 tip SHA를 적는다. `HEAD`라고 적지 않는다.

## 0.1 이상 판별 — corpus salience

탐지(언제·무엇이 생겼나)와 **이상 판별**(무엇이 이 문명에서 이상한가)은 다른 층이다. 전자가 강해도 후자가 약하면, 사실을 찾고도 의미를 틀린다. 힌트를 받아 물증을 만드는 것은 발굴이 아니라 증거 수집이다.

역사서·정적분석에 올리기 전에 묻는 질문:

```
이 저장소에서 평범하지 않은 것은 무엇인가?
평범하지 않다고 말할 corpus-level 근거는 무엇인가?
새 메커니즘이 등장하기 전, 같은 필요를 무엇이 대신하고 있었는가?
이 단위의 정책·규칙·상태전이는 어디에 표현되어 있는가?
그것을 한 곳에서 읽을 수 있는가, 아니면 제어흐름을 실행하듯 추적해야 복원되는가?
같은 상태축·행위축이 **표·객체 없이** 분기에만 반복되는가? (representation **부재**. shift의 전제.)
같은 입력과 같은 최종 출력을 다루는데, 중간에 세계를 표현하는 단위가 바뀌었는가?
DB가 있는 단위에서, 그 정책이 **테이블 컬럼의 타입·널·인덱스**로 읽히는가, 아니면 컬럼은 칸만 있고 의미는 코드인가?
행의 질량이 코드의 질량과 같은 도시를 가리키는가?
```

마지막에서 둘째·셋째는 Git 3층이 아니다. **현재 화석에 테이블이 있으면 스키마와 행 분포를 걷는다.** 코드만 걷고 닫으면 실패할 수 있다(예: 화면 3개인데 한 종류가 관리 행의 99%, `date`와 `varchar`가 같은 ‘일자’, 이름만 비슷한 다른 테이블). 점수제·전체 덤프·별 ‘스키마 고고학’ 장을 두지 않는다. 질문은 representation과 같다: 세계가 어디에 어떻게 적혀 있는가.

코드 쪽 마지막 두 줄은 **부재 다음 shift**다. 새 파일·rename·대량 diff·`@Deprecated`보다 Git에서 약하게 잡힌다. 예: 상태·행위가 분기에만 있음(부재); 문자열→테이블, 조건문→정책 객체(shift). LOC/churn으로 세지 않는다. 점수제(변곡 1~5)를 두지 않는다.

세 번째가 없으면 디렉터리·프레임워크·주석의 최초 출현을 **발명의 탄생**으로 읽는다.
넷째·다섯째(한곳에서 읽히는가 / 분기에만 반복되는가)가 없으면 분기 밀도·매직 문자열을 **일반 청결 점수**로 읽거나, 반대로 거대한 제어흐름 유적을 **연대만 재고 현재 형태는 안 본 것**이 된다.

**구별:** 「IF가 많다」는 품질평가다. 「정책의 저장 형식이 분기문이다」는 구조적 발견이다. 전자는 채점하지 않는다. 후자는 Signal이다.

- 금지: `magic number 있음 → 나쁨`, `if N개 → God`.
- Signal: 같은 정책축 `A×B`가 서로 떨어진 연산(조회·삽입·상태변경·후속일자 등)에서 **하나의 representation 없이 반복 재전개**됨. canonical이 제어흐름이다. 코드를 실행(추적)하지 않고는 정책을 복원할 수 없다.

**제어흐름 기각 게이트 (실행 invariant).** 「일반 smell을 채점하지 마라」는 억제는 강하다. 그 뒤에 **기각 전에** 반드시 물을 단계는 약하면 안 된다. 대형·다분기 코드를 LOC/IF 점수·온보딩으로 내리기 **전에**:

> 그 분기들이 **같은 정책축·상태축·행위축**을 반복적으로 encode하는가?

반복하면 IF/LOC 수는 Signal이 아니다. **그 제어흐름이 canonical을 대신한다는 사실**은 Signal이다. 확인 없이 `IF 많음 → smell → 기각`으로 도망가면 절차 위반이다. 모든 분기를 표로 옮기라는 처방이 아니다. 같은 축의 재전개 여부만 먼저 판정한다.

### 초견 마찰 (first-pass friction) — 가설 생성기, Signal 아님

기본 브랜치 스냅샷을 처음 펼친 뒤, Git 연표를 쓰기 **전에** 아래를 적는다. `[확정]`이 아니다. §0.2의 기억과 같다: **사실이 아니라 구조 가설 생성기.** 그대로 역사서에 넣지 않는다. 버리지도 않는다. 예측 흔적으로 번역해 죽인다.

```
무엇을 알아내려고 할 때 파일/분기를 왕복하게 되는가?
한 정책을 문장·표로 재구성하려면 몇 개 조건축을 동시에 기억해야 하는가?
같은 판단이 서로 다른 위치에서 반복되는가?
새 요구 하나의 수정점이 한곳으로 수렴하는가, 여러 곳으로 퍼지는가?
“왜 이렇게 동작하는가?”에 데이터/정책을 읽는가, control flow를 시뮬레이션해야 하는가?
```

숙련자가 큰 파일을 열고 느끼는 인지적 마찰은 압축정보다. 결론(“더럽다”)으로 쓰지 않는다. 위 질문으로 분해한 뒤 corpus·Git으로 검증한다.

마찰에는 발언권이 있고 판결권은 없다. 각 마찰 문장은 코드의 위치(파일·분기·축)를 가리켜야 가설로 남는다. 위치를 대지 못하면 PRESSURE로 올리지 않는다. 이름·폴더 습관을 익히면 사라지는 비용은 온보딩이지 구조 Signal이 아니다. 반대로 “숙련 부족”으로 치워 버리려면 그 해소가 표기 하나인지, 정책을 횡단해야 하는 형태인지를 가른다. 후자면 숙련 탓이 아니다.

청결 잔소리 금지는 유지한다. 금지하는 것은 점수다. 금지하지 않는 것은 **현재 도시를 걷는 비용**을 가설로 올리는 것이다. 연표에 충실하고 그 보행 비용을 설명하지 못하면 **정확한 실패**다.

순서: **현재 형태가 이미 화석이다.** Git은 그 형태가 어떻게 생겼는지를 다음에 설명한다. 왕조 연표만 복원하고 도로망이 왜 찾기 어려운지를 안 쓰면 목적 밖이다.

**Git은 현재 고통의 자격 증명이 아니다.** PRESSURE는 기본 브랜치 **스냅샷**만으로 세운다. 이후 커밋이 없거나 한 개여도, 화면의 행위를 이해하려면 제어흐름을 실행해야 하면 현재 압력이다. Git은 「이 고통이 어떻게 누적되었는가」의 증거다. 3층 점수가 낮다고 현재 압력을 기각하면 절차 위반이다.

### 랭킹 (앞이 무겁다)

1. **희귀성.** corpus에서 1~2회인 annotation·접미사·가드·API·구조를 먼저 후보로 올린다. 한 번만 있는 표지는 자동 조사 대상이다.
2. **부재.** 그 표지가 한 줄 있는 것보다, **나머지 수백에 없다**가 더 무겁다.
3. **runtime identity.** endpoint가 무엇인지 모르면 생사·이주·삭제 여부를 판정하지 않는다. (파일명·URL·빈 이름·레지스트리 키 중 무엇이 spawn/호출 계약인지.)
4. **발명 금지.** 새 구조가 보이면 먼저 그 행위의 **이전 대체물**을 찾는다.
5. **replacement vs variation.** 접미사·사본은 “다른 가지(장비·고객)”인지 “같은 슬롯의 후계자”인지 호출·주석·birth로 가른다. 같은 폴더에 있다고 같은 종류의 포크가 아니다.
6. **일반 code smell ≠ 이 문명의 이상.** 다른 세계에서는 평범한 표지(Deprecated, 하드코딩, 파일 잔존)가 여기선 유일이거나, 여기선 인프라일 수 있다. 반대로 큰 LOC·희귀 파일명·날짜 간격은 feature일 뿐 자동으로 사건이 아니다. **분기 개수 자체는 사건이 아니다.** 기각은 **제어흐름 기각 게이트를 통과한 뒤**에만. 정책을 복원하려면 여러 제어흐름을 횡단해야 하는 상태는 사건 후보다.
7. **정책 표현 형식.** 규칙이 모델·표·설정·전략에 있는지, control flow에 퇴적되어 있는지. 새 요구가 기존 문법(조건 삽입)으로만 흡수되면 정책의 역사는 별 파일이 아니라 **분기 자체**에 쌓인다.

발견 직후 “안 지웠다 / 커졌다 / 나뉘었다”를 제목으로 쓰지 않는다. 그 행위가 **이 문법에서 기본값인지**를 먼저 본다. 기본값이면 희귀 사건 후보에서 내린다. **예외:** 그 기본값이 정책의 canonical 저장 형식이고, 같은 흡수가 Git에서 반복되면, 사건은 희귀 커밋이 아니라 **그 반복 자체**다. FIRST CONTACT는 어느 문법을 볼지 가리킬 뿐, 반복이 사건임을 증명하지 않는다. 문법 사전 + 커밋 열이 증명한다. 역사는 특이한 사건만의 역사가 아니다. 반복된 평범함의 역사이기도 하다.

salience(희귀·부재)만 강하게 돌리면 그 누적을 놓친다. 희귀한 표지는 잘 찾고, 너무 평범해서 아무도 사건으로 안 여긴 퇴적(조건 삽입 10회 = 기능 추가 10개가 아니라 흡수 문법 1개)을 못 본다. 랭킹 1–2와 랭킹 7은 competing이 아니라 **다른 종류의 화석**이다. **현상 FIRST CONTACT를 쓸 때는 랭킹 7·기각 게이트가 랭킹 1보다 앞선다.** 희귀 annotation을 먼저 사냥해서 수행 인터프리터를 건너뛰지 않는다.

### 문법 사전 (이 단위의 평범함)

salience는 빈 머리로 돌리지 않는다. 각 조사 단위 역사서 앞머리에 **평범함 5줄**을 둔다. 이미 Closed된 상위 서사에서 가져오거나, 런타임 배선(누가 이 파일을 어떤 이름으로 부르는가)에서 뽑는다. 랭킹은 그 5줄에 대해 한다.

일반 청결 규칙(매직넘버 금지, 죽은 코드 삭제, Java Deprecated 관행)으로 이 숲을 채점하지 않는다.

### 산출 형식

이상 후보는 기존 서사를 확인하는 목록이 아니다. **그 서사를 깨뜨릴 수 있는 것**만. 이미 문서에 있는 결론은 제외. 후보마다: corpus 횟수 / 부재 범위 / runtime identity / 이전 대체물 / replacement인지 variation인지 / 문법 기본값 여부.

힌트(“저 파일 봐”) 없이 이 목록이 안 나오면, 그 조사는 발굴이 아니라 수집이다.

## 0.2 구술사 — 기억을 가설 생성기로 (사실로 먹지 않음)

유물(코드)과 층서(Git)만으로 중요도 함수를 복원하지 못할 때가 있다. 그때 당사자 기억은 **사료**다. 정답이 아니다.

```
당사자 기억 → 주장 분해 → 예측 흔적 → Git 반증/검증 → 역사
```

기억을 받자마자 역사서를 쓰지 않는다. 먼저:

1. Git이 아직 설명하지 않은 주장을 뽑는다.
2. 각 주장이 참이라면 **어떤 코드/Git 흔적이 있어야 하는지** 예측한다.
3. 기본 브랜치에서 그 흔적을 찾는다.
4. 맞으면 `[당사자 회고]` + Git 정합. 틀리거나 침묵이면 **충돌/공백을 보고**한다. 기억을 고치지 않고, Git을 맞추러 기억을 `[확정]`으로 올리지 않는다.

예측 흔적의 예(추상): 새 검증면이 “영향면을 작게 잡아 착지했다”면 — 운영 코드가 러너를 import하지 않음, 저장 단계가 export에서 빠짐, 전 테넌트 일괄 적용이 아님, 공유 빌드 설정은 안 바뀜. 반대를 뚫었다는 주장은 Git에 안 남을 수 있다. 그 부재를 “반대가 없었다”로 읽지 않는다.

발굴 위치를 지정하는 것(“저 파일”)과 지도를 주는 것(기억 통째)은 다르다. 후자만 받는다. 전자는 수집기다.

타인의 의도·조직 음모는 구술로도 `[확정]`이 아니다. 본인의 판단·본인이 한 일·본인이 느낀 비용만 회고 칸에 둔다.

Git은 **날짜와 착지한 형태**를 남긴다. 왜 그 형태 없이는 버틸 수 없었는지는 남기지 않는다. 그 공백을 날짜의 성숙으로 채우지 않는다.

조사는 두 번이다. **1차** 기본 브랜치만, 회고 없이. 스냅샷 초견 마찰(§0.1)로 가설을 세운 뒤 물증화한다(당사자도 안 중요하게 여긴 물증 포함). **2차** 회고로 그럴듯한 오독을 깨뜨린다. 서사가 선 뒤에는 “더 찾기”를 하지 않는다. **명제를 죽일 반례만** 본다. 문장을 고칠 정도가 아니면 버린다. 부재도 종류가 다르다: 회고상 못 올린 것 vs 애초에 Git에 계획조차 없는 것. 한 ‘음화’로 묶지 않는다.

## 0.3 재조사 — 증거는 남기고 위계를 고친다

§0.2의 1차/2차를 전제로 한다. 기존 산출물을 폐기하고 처음부터 다시 캐지 않는다. `[확정]` Git 연표·경로·커밋은 **자산**이다. 다시 하는 것은 **질문의 순서와 중요도 판정**이다. 아래 금지·의무는 목적 절 세 invariant의 파생이다. 같은 방어를 늘리지 말고 그 표로 돌아간다.

옛 순서(금지에 가깝다): Git → 특이 사건 → 정적 수치 → 역사 → 현재 위험.  
새 순서:

```
현재 코드를 걷는다 (가능하면 옛 보고서를 아직 안 읽고)
현상 FIRST CONTACT: 과제 없이 객체를 열면 무엇이 이해를 방해하는가 (행위가 문장으로 안 읽힘)
변경 FIRST CONTACT: 규칙 하나. 왕복·작업기억·수정점·검증면. 현상의 괴물을 이웃으로 밀어 끝내지 않음
마찰을 구조 명제로 분해한다. 다분기를 기각하기 전 기각 게이트
현재 코드로 검증한다 (이제 Signal)
Git에서 그 형태의 퇴적사를 찾는다 (기존 [확정]을 재사용)
옛 역사에서 인과적 위계를 교정한다. 역사적 중요도는 이 단계에서 지우지 않는다
```

이 순서는 **이번 고통의 퇴적**을 찾기 위한 조사 경로다. 그 경로가 지나가지 않은 `[확정]` 시대를 산출에서 지우는 순서가 아니다. 단계 6의 「교정」은 왕관을 옮기는 일이지 도시를 허무는 일이 아니다.

재조사에서 먼저 볼 셋:

1. **FIRST CONTACT를 둘 다 새로 쓴다.** 현상(이해 방해)과 변경(왕복). 「뭐가 나쁜가」가 아니다. 변경만 쓰면 절차 위반.
2. **옛 PRESSURE를 심문한다.** 「이게 처음 느낀 고통 중 무엇을 설명하지?」 답 없는 LOC·churn·author 수는 **측정치로 강등.** 예전에 smell로 버린 것이 그 고통을 설명하면 **승격.**
3. **사건을 현재 지형에서 역추적한다.** 「연도에 X 추가」가 아니라 「이 지형은 어떤 반복으로 생겼나.」 같은 커밋 10개가 같은 흡수 문법이면 역사적 사건은 그 열 개가 아니라 **반복 자체.**

판정을 둘로 가른다. **사실이 틀렸는가** vs **사실은 맞고 중요도가 틀렸는가.** 후자가 재조사의 주된 수확일 수 있다. 목적함수가 뒤늦게 붙은 것이지, 증거가 처음부터 썩은 것이 아닐 수 있다. 정확한데 **대상을 잘못 설명하는** 역사서가 정확한 실패다.

Closed된 단위도 이 위계 교정이 필요하면 연다. 「더 찾기」가 아니다. 놓친 희귀 커밋이 아니라 **놓친 질문**이다. 2차 회고는 1차(회고 없이)가 끝난 뒤에만.

**조사 과정은 독립적이어야 하고, 최종 문서는 자립적이어야 한다.** 둘을 한 금지로 합치지 않는다.

- 조사: 가능하면 옛 보고서를 아직 안 읽고 FIRST CONTACT를 쓴다. Git 연표·SHA를 처음부터 다시 캐지 않는다. `[확정]` 자산은 재사용한다.
- 산출: 역사서·정적은 **그 파일만 연 독자가** 「무엇이 태어났고 → 무엇이 변했고 → 무엇은 안 변했고 → 그래서 오늘 왜 여러 곳을 고치는가」를 따라갈 수 있어야 한다.

금지하는 것은 옛 연표를 본문의 왕으로 되살리는 것, 그리고 Git을 중복 발굴하는 것이다. 금지하지 않는 것은 **이미 `[확정]`인 시대 의미·변화 방향을 새 질문에 맞게 다시 서술하는 것**이다. 「재수집하지 않는다」를 「새 문서에 쓰면 안 된다」로 읽지 않는다. 옛 시대를 이름만 남기고 「연표는 펼치지 않음」으로 외부에 미는 산출은 역사서가 아니라 판결 메모다. 그건 실패다.

이유를 모르면 모른다고 쓴다. 출생 시점과 설계 이유를 한 문장으로 합치지 않는다.

**FIRST CONTACT의 원인과 시대의 역사적 중요도는 같은 축이 아니다.** 위계 교정은 「오늘 이 고통을 만든 변곡점」이라는 **지위**를 옮기는 일이다. 그 시대가 문명에서 실제로 변곡이었으면, 원인이 아니어도 변곡으로 남긴다.

금지:

- 이번 질문과 직접 연결되지 않는다고 해서 `[확정]` 다축 시대(재현·관측·분해·장애 추적이 같이 움직인 막)를 한 줄 변경 요약으로 납작하게 만들기.
- 옛 보고서가 그 시대를 「오늘의 핵」으로 과대평가했다고 해서, 새 역사서에서 그 시대의 **의미 자체**를 삭제하거나 배경 두 문장으로 강등하기.
- FIRST CONTACT에 필요한 사건만 남기고 나머지 확정 연표를 증발시키기. 필요한 것은 왕관의 위치이지, 도시의 철거다.

허용·의무:

- 그 시대를 자산에서 재서술할 때, 당시 무엇이 같이 움직였는지(축)를 독자가 복원할 수 있게 쓴다. Git을 다시 팔 필요는 없다.
- 그 다음에 경계 문장을 붙인다: 그 개혁/막이 **이번 변경 과제의 수정점을 만들었는가, 안 건드렸는가.**
- 두 진실을 동시에 보존한다. 「그 시대는 중요한 변곡이었다」와 「그러나 오늘의 이 횡단 고통을 만든 변곡은 아니었다」.

정적 PRESSURE에서도 같다. 이번 과제가 설명하지 않는다고 해서 확정된 응력 파일을 「없는 일」로 지우지 않는다. 측정치·이웃 칸에 **무엇인지는 남기고**, 이번 고통의 원인 자리만 비운다.

**재조사는 역사적 사건을 FIRST CONTACT와의 인과거리만으로 승격·강등하지 않는다.** 옛 사건·시대마다 판정을 **둘** 한다. 한 점수로 합치지 않는다.

| 축 | 질문 | ①이 아니어도 |
|----|------|----------------|
| 인과적 중요도 | 현재 변경 고통을 설명하는가? | 핵 자리를 비운다 |
| 역사적 중요도 | 이 사건 이후, 같은 종류의 코드를 작성하는 **문법·representation·책임 경계·실행/배포 topology·검증 방식** 중 하나가 달라졌는가? | ①이 거짓이어도 YES면 **사건/시대로 보존**한다 |

`인과 무관 × 역사 변곡`은 예외가 아니다. **정상적인 1급 결과**다.

인과축과 역사축은 독립적으로 판정한다. FIRST CONTACT에 대한 설명력이 낮다는 이유로 역사적 변곡을 축소하지 않는다.

물리적 분리보다 의미론적 탄생이 먼저일 수 있다. 새 파일·클래스·모듈의 birth를 새로운 작성법의 birth로 동일시하지 않는다.

재조사에서 고치는 것은 **현재 핵과의 인과적 위계**이다. 독립적으로 입증된 역사적 중요도를 고치는 것이 아니다.

`FIRST CONTACT는 발굴의 초점을 정하지만 역사의 존재론을 결정하지 않는다.`

## 0.4 통제변수 ≠ 산출 목적함수

조사 규율과 산출물 보존 규율은 다른 층이다. 전자를 후자의 목적함수로 일반화하면 같은 실패가 두 얼굴로 난다.

| 통제변수 (조사) | 과잉 일반화 (산출) | 결과 |
|-----------------|---------------------|------|
| 옛 보고서를 읽고 조사하지 않는다 | 옛 `[확정]`을 새 문서에 쓰지 않는다 | 판결 메모. 자립 실패 |
| FIRST CONTACT로 초점을 고정한다 | 현재 고통을 설명하지 않는 역사는 중요하지 않다 | 독립 변곡이 한 줄 요약으로 증발 |

둘 다: **방법론적 통제변수를 산출물의 목적함수로 과잉 일반화한다.**

고치는 대상은 단건 문장이 아니라 이 일반화다. 실행: §0.3 이축, §4 단계 2a(독립 역사 sweep) → 3a 교차, §16 승격(배율).

## 1. 산출물은 두 문서로 분리한다

고고학 조사의 산출물은 **정적분석 보고서**와 **역사서**로 나뉜다. 둘은 목적이 다르고 독자가 다르다. (파일명·위치는 각 저장소가 정한다 — 이 문서는 역할만 규정한다.)

### 정적분석 보고서

**질문**: "지금 이 코드의 구조적 상태는 어떤가? 지금 이곳은 왜 걷기 힘든가? 변경하려는 사람이 처음 지불하는 비용은 무엇인가?"

**순서**: **현상 FIRST CONTACT → 변경 FIRST CONTACT** → PRESSURE(그 체감의 분해) → 규모·churn 등 측정치. 측정치는 진단이 아니다. 체감 없는 PRESSURE는 건물 수·도로 연장만 적고 끊긴 길을 안 적은 것과 같다.

**FIRST CONTACT** (숫자 금지. 아직 Signal 아님):
- (현상) 과제 없이 열면 가능한 행위의 의미가 한곳에서 읽히는가. 못 읽으면 무엇이 방해인가.
- (변경) 한 변경 의도를 들고 열면 무엇이 안 보이는가.
- 한 정책/규칙을 어디서 읽는가. 한곳인가 횡단인가.
- 고친 뒤 맞는지 어디에 가서 아는가.
- 대응 위치를 못 댄 마찰, 표기 습관으로 해소되는 마찰은 여기 적고 PRESSURE로 올리지 않는다. 「길다」만으로 분석을 **종료**하지 않는다. 기각 게이트 전이다.

그 다음 PRESSURE가 체감을 구조로 분해한다. 각 항목에 묻는다: **처음 느낀 고통 중 무엇을 설명하는가.** 답이 없으면 측정치로 내린다. 답이 있는데 예전에 smell로 버렸으면 올린다. 발견한 사실을 그 고통의 원인으로 **전부 배열하지 않는다.** 설명하지 않는 사실은 다른 칸이거나 측정치다.

**내용**: PRESSURE 표(파일별 크기·churn·fan-in·co-change·위험도) · Dead/Zombie 목록 · TODO/FIXME 현황 · 성장곡선(연도별 LOC/파일 수) · co-change 상위 쌍 · fan-in 허브 · **AUTHORSHIP / OWNERSHIP**(파일×작성자 클러스터).

**성격**: 현재 스냅샷의 상태 평가. 수정자가 파일을 열었을 때 겪는 비용이 숫자 뒤에 남아 있어야 한다. 수치만 있고 그 비용이 안 읽히면 정적 실패다.

### 역사서

**질문**: "오늘 개발자가 한 규칙을 고치려 여러 곳을 횡단해야 한다면, 그 형태는 한 번의 설계가 아니라 어떤 반복의 누적인가?"

이 질문은 **렌즈**다. 역사서는 FIRST CONTACT의 기원만을 적는 인과 보고서가 아니다. FIRST CONTACT는 무엇을 핵심 질문으로 삼을지를 정하지, 시대의 존재 여부를 결정하는 **필터가 아니다.** 독립적으로 확인된 변곡점은 현재 질문의 직접 원인이 아니더라도 시대 서사에 남긴다. 단, 사건마다 인과(직접/간접/무관)와 역사(변곡/비중요)를 따로 붙인다(§4 3a).

좋은 통섭은 「연도에 파일이 갈라졌다」에서 끝나지 않는다. **현재 변경 고통이 어느 습관의 퇴적에서 왔는가**까지 가되, 그 습관과 무관한 확정 변곡을 지우며 가지 않는다.

**내용**: 사건 연표(변곡점 중심) · 각 사건의 의미·영향·후속 · **사건 단위 개발자 계보(소유권 전환)** · 시대 구분 · 통섭(이 코드베이스의 문명적 성격).

시대 구분은 이번 FIRST CONTACT의 원인 목록이 아니다. **그 단위 문명에서 막이 바뀐 곳**이다. 원인 지위가 다른 시대로 옮겨도 막의 서사는 유지한다. 축이 여럿인 막을 「로깅·추출·잔존」 같은 변경 나열로 바꾸지 않는다.

역사서에 매 커밋 `작성자: XXX`를 붙이지 않는다. 사람 이름만 늘고 사건 구조가 흐려진다. **사건·시대 단위로 ownership transition을 기록**한다.

**성격**: 시간 축의 서사. 정성적. 설계 결정의 맥락을 제공. **이 파일만으로 시대의 의미가 복원돼야 한다.** 다른 역사서·판결문을 전제로 한 메모는 역사서가 아니다.

### 관계

정적은 **현재 도시의 보행 비용**이고, 역사는 **그 도로망을 만든 반복**이다. 정적이 증거, 역사가 해석인 관계는 유지한다. 한 문서에 섞지 않는다. SHA·author·rename만 정확하고 현재 형태를 설명하지 못하면 실패다. 위계만 맞고 시대 서사가 빠져 있어도 실패다.

## 2. 역사서 작성을 위한 3층 사건 탐지 프레임워크

3층 탐지는 Git에서 **사건 후보**를 찾는 장치이지, 역사적 변곡의 완전한 탐지기가 아니다. representation **부재·shift**와 반복된 변화 문법은 현재 구조(§0.1) 및 §4의 독립 역사 sweep에서 별도로 판정한다. 4층으로 올리지 않는다. 그건 커밋에서 자동 추출되는 사건 종류가 아니라 여러 화석을 종합하는 의미론이다.

역사서를 쓰려면 먼저 **사건을 식별**해야 한다. 사건 **탐지**에는 3개 층위가 필요하다. 인간 층(§14)은 이 3층에 얹지 않는다 — author를 scoring에 넣으면 머지 게이트키퍼·계정 별칭·대신 커밋이 변곡점으로 승격된다.

### 1층: 물리적 변곡점 (자동)

**탐지 대상**: 대량 rename, 대량 delete, 대량 insert, 디렉토리 생성/소멸.

**방법**: `git log --shortstat` + `--diff-filter=R` 조합으로 각 커밋의 구조적 규모를 scoring.

**scoring 기준(예시 임계값 — 저장소 규모에 맞게 조정)**:
- 삭제 200줄 이상 → score += 삭제량/100
- 추가 500줄 이상 → score += 추가량/200
- rename 3건 이상 → score += rename수 × 2
- 파일 20개 이상 변경 → score += 파일수/5
- 총 churn 1000줄 이상 → score += churn/500

**강점**: 규모가 큰 거대 사건을 놓치지 않음.
**한계**: 규모는 작지만 방향을 바꾼 사건(설계 선회)을 놓침.

### 2층: 개념 탄생 (자동)

**탐지 대상**: 새 Entity/Service/Repository/Component 파일의 최초 출현.

**방법**: **기본 브랜치 트리**의 해당 스택 파일 목록(예: `*Entity.*`, `*Service.*`, 컴포넌트·스토어)을 `git ls-tree -r --name-only <default>`로 추출한 뒤, 각 파일의 `git log <default> --diff-filter=A --reverse -1`로 최초 커밋을 식별. 워킹트리 glob으로 목록을 만들지 않는다.

**의미**: 파일 하나의 탄생이 곧 **새 도메인 개념의 탄생**일 수 있다.
- `<외부통합>Service` 최초 출현 = 그 통합(예: LLM·결제·메시징)의 시작.
- `<핵심>Entity` 최초 출현 = 단일 테이블 상속(STI) 같은 도메인 모델 결정의 물증.

**강점**: 규모와 무관하게 "새 개념의 출현"을 잡음.
**한계**: rename에 의한 재생성과 진짜 탄생을 구분하려면 커밋 메시지 참조 필요.

### 3층: 설계 결정 (반자동)

**탐지 대상**: 커밋 메시지의 구조적/아키텍처적 결정 키워드.

**키워드 패턴**:
```
한국어: 수렴, 폐기, 제거, 삭제, 전환, 도입, 통합, 분리, 재편, 흡수, 걷어내기
영문:   remove, delete, merge, split, introduce, deprecate, replace, migrate, absorb, converge
패턴:   →, ->, 패키지.*변경, 구조.*변경
```

**방법**: `git log --format="%ad|%H|%s"` 전체를 키워드 매칭. 복수 키워드 매칭 시 고신뢰.

**강점**: 규모는 작지만 방향을 바꾼 결정을 잡음 — 문서 몇 줄짜리 "설계 확정" 커밋이 이후 모든 작업의 분기점인 경우.
**한계**: 키워드 없는 결정은 놓침. false positive 있음(단순 rename도 `→`로 걸림) — 에이전트 판단으로 필터링.

## 3. 사건 묶기 (4층 — 수동/에이전트 초안)

3개 층에서 추출한 개별 커밋을 **하나의 역사적 사건**으로 묶는다. 묶인 사건에는 코드·시간·인과와 함께 **개발자 계보**를 채운다(§14).

**원칙**:
- 같은 주(week) 안, 같은 목적의 연속 커밋 = 하나의 사건.
- "도입 → 폐기"가 24시간 이내면 "실험"이라는 단일 사건.
- rename + 이전 이름 삭제 = "이름 혁명" 하나.
- Phase 1/2/3… = "○○ 수렴"이라는 하나의 사건(각 phase는 sub-event).
- 법·조직 마커(저작권, 사명, LICENSE)와 실제 committer 집단 교체는 **별 사건**일 수 있다. 시간적으로 인접해도 자동으로 동일시하지 않는다.

**추상 예시**:
```
사건: 단명 실험 (도입일 ~ 익일)
  - Day N   : <개념> 도입 (+대량 줄, 다수 파일)
  - Day N+1 : <개념> 폐기, 다른 구조로 수렴 (−대량 줄)
  의미: 24시간 만에 대체 구조로 흡수된 시도.
```
```
사건: 대량 rename 혁명 (연속 며칠)
  - oldPrefixA → newPrefixA (수백 renames)
  - oldPrefixB → newPrefixB (수백 renames)
  의미: 이름의 혁명. 이후 git --follow 분석에 영구 영향(전후를 갈라 읽어야 함).
```
```
사건: 소유권 전환 [확정]
  - <commit> — 명목 마커 (저작권/사명 A→B)
  개발자 계보: 그 전 시대의 주 author 클러스터 P,
                전환 전후 실작업 클러스터 Q,
                이후 개혁·유지 클러스터 R
  해석: 명목 마커와 실제 유지보수 주체의 이동이
        일치하는가 / 어긋나는가. 어긋나면 별 사건으로 남긴다.
```

## 4. 작업 순서

1차와 2차를 섞지 않는다. Git 3층은 FIRST CONTACT·현재 구조 다음이다.

**1차** (회고 없이. 기본 브랜치만)

```
0.  기본 브랜치 고정. 워킹트리·HEAD·다른 브랜치로 확인한 내용은 버린다.
0a. FIRST CONTACT. **현상**(이해 방해) 다음에 **변경**(과제 하나·왕복·검증면). 숫자·Signal 아님. 변경이 현상의 괴물을 지우지 않음.
0a-gate. 다분기/대형 코드를 온보딩·smell로 내리기 전: 같은 상태·행위 축의 재전개인가. 맞으면 부재가 Signal.
0b. 현재 구조 검증. 정책·규칙이 어디에 있는가 / 한곳에서 읽히는가. 마찰 → 명제 → 코드로 죽임.
0c. 문법 5줄 + salience (희귀·부재). 발명 전에 이전 대체물.
    랭킹 7: 평범한 흡수 문법의 반복도 화석. 희귀만 찾지 말 것.
1.  Git 3층 탐지 (그 형태·그 반복의 퇴적사). 기존 [확정] 재사용 가능.
2.  사건 묶기. 기능 추가 N회가 같은 흡수면 사건은 반복 자체.
2a. 독립 역사 sweep. 이 단계에서 FIRST CONTACT를 잠시 잊는다.
    representation이 바뀌었나 / 책임 경계 / runtime·deployment topology /
    새 병존·포크 / 검증·관측 / 변화 문법 자체.
    YES면 역사 변곡 후보. FC 설명력으로 축소하지 않는다.
    `@Deprecated`·rename·모듈 birth는 탐지 힌트이지 변곡의 정의가 아니다.
3.  역사서 초안 — sweep으로 살아 있는 시대 + 현재 고통의 퇴적. 후자만으로 시대를 자르지 않는다.
3a. 교차. 각 시대/사건에 **두** 판정을 붙인다. 한 enum으로 합치지 않는다.
    인과: 직접 / 간접 / 무관
    역사: 변곡 / 비중요
    `인과 무관 × 역사 변곡`은 1급 결과. 시대 의미를 복원한 뒤 이번 질문과의 경계를 긋는다.
    인과=직접 → 현재 서사의 핵. 인과=간접 → 연결을 명시하고 축은 남긴다.
    역사=비중요 → 필요하면 측정치/부록으로 내린다.
    `인과≠직접`을 `삭제` 또는 `두 문장 압축`으로 바꾸지 않는다.
4.  정적보고서 — 현상 FC → 변경 FC → PRESSURE(체감 심문) → 측정치. 「길다/IF」로 PRESSURE를 끝내지 않음.
```

**2차** (1차가 끝난 뒤만)

```
§0.2 회고: 주장 분해 → 예측 흔적 → Git. 충돌은 숨기지 않음.
§0.3 재조사면: 사실 오류 vs 중요도 오류. 위계만 고친다. 자산 폐기 금지.
    사건마다 인과와 역사를 따로. §4 단계 2a sweep을 건너뛰지 않는다. 3a는 교차이지 sweep 대체이 아니다.
```

3층 스크립트(shortstat·birth·키워드)는 1차의 단계 1이다. FIRST CONTACT보다 앞에 두지 않는다.

## 5. 증거 비용 참조

| 분석 | 비용 | 강도 | 비고 |
|------|------|------|------|
| 1층 shortstat scoring | ~1분 | 강 | 전체 히스토리 구조 변동 |
| 2층 concept birth | ~5분 (파일당 git log) | 중 | 새 도메인 개념 식별 |
| 3층 keyword match | ~30초 | 약~중 | false positive 있음, 에이전트 필터 필요 |
| 4층 사건 묶기 | ~30분 (수동) | 강 | 역사적 해석 |
| identity cluster + 시대별 shortlog | ~5–15분 | 중~강 | 커밋 수가 적을수록 가성비 큼 |
| 파일×작성자 (상위 응력 파일만) | ~5분 | 중 | blame 전 파일 순회는 하지 않음 |
| 정적분석 (churn/fan-in/co-change) | ~3분 | 강 | 현재 상태 평가 |

## 6. 과잉조사 중단 조건

역사서 작성은 아래 중 하나를 만족하면 중단한다:

- 주요 시대 구분이 확정되고, 각 시대의 대표 사건이 1개 이상 식별됨.
- 각 시대의 주 author 클러스터가 안정됨(사람 층 포화).
- 새 층위를 추가해도 기존 사건 목록이 바뀌지 않음(포화).
- 조사 비용이 역사서 가치를 초과(개인 프로젝트 기준: 4시간 이상이면 재고).
- **기본 브랜치로 재확인하지 않은 초안**은 수정하지 않고 폐기한다(§0).
- 파일별 blame 전수 조사에 들어가려 하면 중단. AUTHORSHIP은 PRESSURE 상위 파일 + 신규 분해 산출물만.
- 남은 질문이 대상 단위의 역사적 형태를 뒤집지 않고 이웃 도메인으로만 이어지면 **Closed**. 그 질문은 열어 두되 이 서사는 재개하지 않는다.

Git의 최근 추세를 미래로 외삽하지 않는다. 개혁 커밋의 연속은 다음 개혁을 약속하지 않는다. **하지 않은 행위**(다음 단계를 안 감, 알고도 안 고침, 삭제하지 않음)는 Git에 원칙적으로 안 남는다. 그 공백을 당사자 회고로 채울 수는 있으나, 아직 관측되지 않은 동결을 Git 사실로 쓰지 않는다. 가족 닮음(같은 계열의 실패)을 **단일 root cause**로 허위 통일하지 않는다.

Git에 테스트가 나타난 것을 **조직의 테스트 문화 성숙**으로 읽지 않는다. Git에 테스트가 없는 것을 **테스트를 하지 않았다**로 읽지 않는다. 시간축에 놓인 추출·검증 커밋을 한 저자의 한 프로그램으로 잇지 않는다.

큰 클래스마다 별도 역사서를 만들지 않는다. 승격 기준은 §16.

## 7. 보고서 서식 원칙 — PRESSURE 항목의 3단 분리

모든 PRESSURE 항목은 **Signal → Interpretation → Action**으로 분리한다. 증거(사실)·해석(판단)·권고(행동)를 한 줄에 섞지 않는다.

### 서식 (추상 예시)

```
Signal (확정된 사실)
  - 크기: 매우 큰 단일 파일 (LOC·바이트 수치)
  - fan-in: 소수 진입점에서만 호출
  - churn: 낮음
  - revert/hotfix: 0건

Interpretation [강한추정]
  - 한 파일에 여러 관심사 혼재 **이거나**, 같은 상태·행위 축이 분기에만 반복(canonical 부재). 기각 게이트 전에 God/온보딩으로 단정하지 않음
  - 현재는 안정적이나, 다음 기능 추가 시 팽창 관성이 살아있음

Counter Evidence
  - churn 낮음 = 자주 안 건드림 = 현재 폭발 아님
  - 테스트 존재 + 1:1 co-change = 커버리지 있음
  - fan-in 낮음 = 외부 영향 범위 제한적

Time Horizon
  - 현재: 안정 (위험도 ⚪)
  - 확장 시: 높음 (위험도 🔴) — 새 관심사/축 추가 시

Action
  - 즉시: 없음
  - 중기: 분해 검토 (<관심사A>/<관심사B>/<관심사C>/Orchestrator 로 추출)
  - 근거: Signal의 "매우 큰 단일 파일" + "관심사 혼재" → 단일 변경의 영향 범위 예측 불가
```

### 원칙

- **Signal**에는 `[확정]`만. 수치·파일 목록·git 출력 등 검증 가능한 사실.
- **Interpretation**에는 반드시 Confidence 등급을 붙인다.
- **Counter Evidence**는 해석에 반대되는 증거를 명시한다("무조건 나쁜 건 아니다"를 읽는 사람이 이해하게).
- **Time Horizon**은 최소 2단계(현재 / 확장 시). 팀 프로젝트는 3단계(현재 / 6개월 / 확장 시).
- **Action**에는 "근거: Signal의 어떤 항목이 이 권고를 만들었는가"를 역참조한다.
- 고 churn 파일의 Interpretation에는 AUTHORSHIP 분포를 병기할 수 있다(§15). 위험도 칸에는 이름을 넣지 않는다.

## 8. Confidence 등급은 보고서에서도 유지한다

이 프로토콜의 증거 등급(아래)을 보고서 산출물에서도 그대로 쓴다.

```
[확정]       코드/Git/DB/설정/문서에서 직접 확인
[강한추정]   복수 정황을 일치시킨 추정 (반증 없음)
[미확인]     증거 부족, 아직 단정 불가
```

**적용 위치:**
- PRESSURE 표의 "응력 유형"(Interpretation) → 등급 필수.
- co-change 해석("독립 변경 불가능") → `[강한추정]`.
- Dead/Zombie 판정 → 빌드 미포함이면 `[확정]`, 사용 여부 미확인이면 `[강한추정]`.
- Git 필드(author/committer/날짜) → `[확정] Git author`.
- "이 사람이 설계했다 / 실질 담당이다" → 반드시 `[추정] 실질 담당`. 페어, 대신 커밋, 코드 복사, 최초 이식을 설계와 동일시하지 않음.

## 9. "하지 말아야 할 것" 절

보고서 마지막에 반드시 포함한다. 구조적 위험의 존재가 즉시 행동으로 이어지는 오독을 방지한다.

### 서식 (추상 예시)

```
이번 조사에서 권장하지 않는 행동

- <대형 God 파일> 즉시 분해 — churn 낮고 장애 없음. 분해 비용 > 현재 리스크.
- <고 fan-in 공통 축> 대규모 리팩터 — 현재 안정. 확장 시에만 리스크 현실화.
- <미배선 평행 표면> 즉시 삭제 — 명시적 폐기 결정을 먼저 내린 뒤 삭제.
- <진행 중 재설계> 강행 — 병행 작업의 자연 지연을 사고로 분류하지 않음.
- 커밋 author로 기여자를 평가·서열화 — 인간 층은 지식의 소재와 단절을 복원하는 층이다.
- 매 커밋에 작성자를 나열 — 사건 단위 전환만 기록.
- 최초 대량 insert의 author를 "이 코드를 만든 사람"으로 단정 — 기본 해석은 "repository에 넣은 사람".
- 명목 소유권 변경(저작권/사명)을 실제 committer 교체와 동일시.
- 초견에서 불편했다고 해서 이후 발견한 사실을 그 불편의 설명으로 전부 배열하기.
- 이번 변경 과제의 원인이 아니라고 해서, 이미 변곡으로 확정된 시대를 삭제하거나 한 줄 요약으로 강등하기.

근거: "구조적으로 위험한 것"과 "지금 고쳐야 하는 것"은 다르다. **오늘의 핵이 아닌 것**과 **역사에 없었던 것**도 다르다.
시한폭탄은 제거 계획을 세우되, 폭발하지 않는 한 당장 해체하지 않는다.
```

## 10. Counter Evidence 원칙

모든 "위험" 판정에는 반대 증거를 병기한다. 한쪽만 보여주는 보고서는 신뢰를 잃는다.

**의무 기재 조건**: PRESSURE 표에서 위험도 🟠 이상인 항목은 Counter Evidence 필수.

**추상 예시**:

| 항목 | 위험 해석 | 반대 증거 |
|------|-----------|-----------|
| 초대형 단일 서비스 | God Object | churn 낮음, 장애 0, 테스트 존재 |
| 두 컴포넌트 고빈도 co-change | 강결합 | 계층 관계상 자연스러운 면, 후속 리팩터 기회 있음 |
| enum/유틸 초고 fan-in | 허브 리스크 | 값 추가는 기존 코드 안 깨뜨림, 안정 축 |

## 11. 권고의 근거 역참조

모든 권고(Action)에는 "이 권고를 만든 증거"를 명시한다. 읽는 사람이 "왜?"를 물을 때 보고서 안에서 답을 찾을 수 있어야 한다.

### 서식 (추상 예시)

```
권고: <대형 God 파일> 중기 분해 검토
근거:
  - Signal: 매우 큰 단일 파일 (LOC/바이트) — PRESSURE 표
  - Signal: 여러 관심사 혼재 — 역사서 해당 장
  - Interpretation: 단일 변경의 영향 범위 예측 불가 [강한추정]
  - Counter: churn 낮음 → "즉시"가 아닌 "중기"로 판정
```

## 12. Time Horizon — 위험의 시간축

"위험하다"만으로는 불충분하다. **언제 위험한가**를 명시한다.

| 시간축 | 의미 | 행동 |
|--------|------|------|
| 현재 | 오늘 폭발 가능 | 릴리스 차단 or 즉시 대응 |
| 단기 (1~2 릴리스) | 다음 기능 추가 시 위험 | 계획에 포함 |
| 확장 시 | 규모/팀/요구 변경 시 위험 | 인지만. 트리거 조건 기록 |

**적용**: PRESSURE 표의 "위험도" 옆에 Time Horizon 칸 추가.

## 13. False Positive History

오판 사례를 기록한다. 같은 실수를 반복하지 않기 위해.

다음 오판이 나면 문장 하나를 더하지 않는다. 먼저 묻는다.

- invariant가 없었는가 → 목적 절 표에 칸을 더한다.
- invariant는 있는데 실행 절차가 어겼는가 → 해당 절의 절차만 고친다.
- 둘 다 있는데 적용이 틀렸는가 → 이 로그에 넣고 그 절차의 강제 분기만 강화한다.

국소 방어문을 쌓아 이 문서를 레거시로 만들지 않는다.

### 서식 (추상 예시)

```
False Positive Log

| 조사 | 초기 가설 | 결과 | 오판 원인 | 학습 |
|------|-----------|------|-----------|------|
| <날짜/저장소> | "legacy 잔존" | 이미 해소됨 | 삭제 이력(--diff-filter=D) 미확인 | 1층 분석 시 삭제 커밋도 함께 추출 |
| <날짜> | 대형 Job = LOC·책임 적층·실행면 부재 | 정책 canonical 없음(동일 축이 연산마다 재전개)을 1차에서 놓침 | 반복 조건을 일반 smell로 보고 salience에서 제외. 청결 잔소리 방지에 과보정 | 「정책은 어디에 표현되는가 / 한곳에서 읽히는가」를 1차 정적 질문에 포함. IF 개수≠사건. 제어흐름을 횡단해야 정책이 복원되면 구조적 압력 |
| 재조사 산출 | 옛 연표를 본문에 안 펼침 = 중복 방지 | 역사서가 판결 메모가 됨. 독자가 시대 의미를 복원하지 못함 | 「재수집 금지」를 「서술 금지」로 읽음. 조사 독립과 문서 자립을 한 금지로 합침 | 조사는 독립, 최종 문서는 자립. `[확정]` 시대 의미는 새 질문에 맞게 다시 쓴다. Git을 다시 팔 필요는 없다 |
| 재조사 위계 | FIRST CONTACT 원인이 아닌 시대 = 역사서에서 압축·삭제 | 다축 변곡이 변경사항 나열이 됨 | 조사 초점(인과)을 산출 존재론(역사)으로 일반화. §0.4 | §4 2a에서 FC를 잊고 역사 sweep. 3a는 교차. `인과 무관×역사 변곡`은 1급 |
| 재조사 탐지 | `@Deprecated`/모듈 birth = 변곡의 정의 | 의미론은 먼저 일어났고 주석·파일 분리는 늦음 | Git에 밝은 선언을 변곡으로 동일시 | representation shift를 salience에 넣는다. 물리적 birth ≠ 작성법 birth |
| 변경 FC만 | 좋은 변경 질문 하나 = 객체의 괴물 | 수행 화면의 상태기계가 분기에만 있음(부재)을 온보딩으로 기각 | 억제(IF 채점 금지)는 강하고, 기각 전 복원 의무는 약함. 변경 FC가 현상 FC를 대체 | FC를 현상/변경 둘. 제어흐름 기각 게이트. 부재는 shift의 전제 |
| Git 빈약 = 압력 없음 | 한 커밋·이후 무변곡이면 현재 구조는 약하다 | 스냅샷의 상태기계 부재를 3층이 안 잡아서 기각 | Git을 현재 고통의 **자격**으로 씀. 누적 설명과 혼동 | PRESSURE는 스냅샷. Git은 어떻게 생겼는지만. 한 커밋이어도 현재 압력 |
```

- **위치**: 적용록 메타 절에 포함. 사례가 3건 이상 쌓이면 별도 문서로 분리(파일명은 저장소가 정함).
- **목적**: 다음 저장소에 적용할 때 "이전에 이런 착각을 했다"를 참조 가능.

## 14. 인간 층 — 소유권과 지식 이동

인간 층은 3층 탐지의 입력이 아니라 **사건 묶기(§3)와 정적분석 AUTHORSHIP(§15)의 규칙**이다.

### 질문 (역사서)

시대·사건마다 아래를 묻는다. 답할 수 없으면 `[미확인]`으로 남긴다.

- 최초 대량 착지(이식)의 Git author와 이후 주 유지보수 클러스터가 같은가?
- 핵심 런타임 개념(타이머 풀, 전송 루프, 인증 등)을 **처음 커밋한** 클러스터는 누구인가?
- 장기 휴면 후 코드를 깨운 클러스터는 누구인가?
- 법·조직 소유권 전환 전후로 **실제 `--no-merges` committer 집단**도 교체됐는가?
- 관측성·모듈 분해·버그헌트를 주도한 클러스터가 동일인가, 축마다 다른가?
- 인접한 두 시대(예: 재가동 vs 이후 규율 도입)의 author 분포가 같은가?

마지막 질문은 통섭 문장을 강하게 만든다. 명목 이관과 공학적 성숙이 **같은 주체**의 연속인지, **다른 세대**의 손바뀜인지를 가른다.

### 전처리: identity cluster

Git author 문자열을 사람 수로 세지 않는다. 먼저 클러스터한다.

**묶는 신호** `[확정]`에 가깝게:
- 동일 이메일, 다른 display name
- 동일 local-part, 도메인만 회사 이전 (`@old` → `@new`)
- 기계 계정명(`HOST\User`) + 같은 이메일

**묶지 않는 것**:
- 같은 날 같은 파일을 만졌다는 이유만으로 동일인 처리
- merge author와 브랜치 실작업 author를 한 클러스터로 합치기

클러스터에는 안정 라벨을 붙인다 (`<cluster-P>`). 보고서에는 라벨과 대표 식별자 하나(이메일 또는 가장 흔한 name)만 적는다.

### 머지 vs 실작업

| 축 | 명령 | 읽는 것 |
|----|------|---------|
| 지식 이동 | `git log --no-merges` | 코드를 넣은 클러스터 |
| 프로세스 | merge 커밋 author | 게이트키퍼·리뷰 경로 |

둘을 한 shortlog에 섞지 않는다. 머지가 많은 저장소에서 게이트키퍼가 "주 저자"로 보이게 된다.

### 역사서 기재 위치

사건 블록 안에 **개발자 계보**를 한 번만 둔다.

```
사건: <이름> [등급]
  - 코드/시간 증거 …
  개발자 계보 [확정] Git author:
    - 이전 시대 주 클러스터: <P>
    - 이 사건 실작업: <Q> (머지: <G>)
    - 이후 주 클러스터: <R> 또는 미형성
  해석 [강한추정|미확인]:
    - 지식의 연속 / 단절 / 명목만 이동
```

통섭에서 "소유권이 넘어온 뒤 규율이 도입됐다"류 문장은 **사람 층으로 재검증**한다. 시간 상관만 있으면 약하게 남기고, 주체 교체(또는 연속)가 `--no-merges` committer 분포로 보이면 강한 주장으로 올린다.

### 하지 말 것 (인간 층)

- Git author = 설계자.
- 최초 대량 LOC 커밋 author = 원작자. 기본값은 **이식자(repo에 넣은 사람)**.
- 저작권/LICENSE/사명 변경 = 유지보수 주체 변경.
- 사람 이름을 PRESSURE 위험도 칸에 넣기.
- Git에 남은 리팩터의 규모를 **저자가 원했던 최종 형태**로 읽기. Git은 착지한 것만 보존한다. 착지하지 않은 다음 단계(음화)는 당사자 회고 없이는 복원되지 않는다.
- 당사자 회고를 `[확정]`과 같은 칸에 두기. 회고는 계획·체감·본인 행동 변화에 한정한다. 타인의 의도·조직 음모는 회고로도 단정하지 않는다.
- 한 시대의 선택압을 **이전 시대의 동기**로 소급하기.
- 「이 조직에서는 구조개선이 불가능하다」로 올리기. 상한은 **지속을 어렵게 하는 선택압의 반복 관찰**이다. 국소 변경·버그픽스가 살아남는 것과, 책임 경계를 옮기는 작업의 생존 비용이 높은 것을 구분한다.
- 구조개선을 금하는 **명시적 발화**가 있어야만 그 압력이 있다고 보기. 발화 없이도 조사 귀속만으로 같은 행동이 학습될 수 있다. 타인의 의도 단정은 여전히 금지.

## 15. 정적분석 — AUTHORSHIP / OWNERSHIP

별도 절. PRESSURE와 결합하되, 위험 점수에 이름을 섞지 않는다.

### 표 (파일 × 클러스터)

대상: PRESSURE 상위 파일 + 최근 분해로 생긴 신규 표면. 전 파일 아님.

열:

| 열 | 의미 |
|----|------|
| 파일 | 경로 |
| 최초 author 클러스터 | `--diff-filter=A` 첫 커밋. 이식 커밋이면 그 사실을 주석 |
| commit count | `--no-merges`, 해당 파일 |
| lines changed | `git log -p`/`numstat` 합 |
| last touched | 마지막 실작업 클러스터 + 날짜 |
| 분포 | 1인 집중 / 소수 / 다수 |

### churn과 결합하는 법

같은 LOC/churn이라도 조직적 의미가 반대다.

| churn | author 분포 | 해석 |
|-------|-------------|------|
| 높음 | 한 클러스터가 대부분 | **고위험 + knowledge concentration** (bus factor 낮음) |
| 높음 | 여러 클러스터가 제각각 | **고위험 + coordination surface** (충돌·맥락 손실) |
| 낮음 | 한 클러스터, last touched 오래됨 | 동결. 그 클러스터가 떠나면 암묵지 유실 |
| 낮음 | 다수 | 공유 유틸일 수 있음. fan-in과 함께 읽음 |

이 해석은 PRESSURE 항목의 Interpretation/Counter에 적는다. 위험도 이모지 자체는 구조 신호(크기·churn·fan-in·장애 이력)로만 매긴다.

### bus factor 추정

정밀 공식은 두지 않는다. AUTHORSHIP 표에서

- 상위 응력 파일 N개 중, 최근 실작업이 동일 1클러스터인 비율
- 그 클러스터가 현재 시대의 주 클러스터와 다른지 (떠난 지식)

정도만 `[강한추정]`으로 적는다.

## 16. 확대 단위 — 객체 일대기의 승격

시스템 역사서와 정적분석(§1) 외에, **한 객체의 책임 진화사**를 별도로 둘 수 있다. 기본값은 두지 않는 것이다. 큰 클래스라는 이유만으로 파일을 늘리지 않는다.

승격은 다음을 **모두** 만족할 때만이다:

1. 상위 시스템 역사의 **변곡점**에서 태어났다.
2. 그 이후 **독자적인 책임 진화**가 있다 (상위 시대 구분에 흡수되지 않는 막).
3. 그 독자적 진화를 상위 역사서 안에서 충분히 서술하면 **상위 서사의 배율이나 중심을 왜곡한다.**

세 조건을 만족하면 상위 역사서에 넣지 않는다. 넣으면 시스템 서사가 그 객체에 잡아먹힌다. 확대경의 배율이 다르다.

3번은 현재 FIRST CONTACT의 고통을 설명하는지와 **무관**하다. 현재 고통과 관계없어도, 자기 생애가 상위 서사를 잡아먹으면 승격한다. 현재 고통을 설명해도, 상위 배율에서 충분히 쓸 수 있으면 승격하지 않고 상위 역사서에 남긴다(§4 3a로 지위만 표시). 승격은 보존이 아니다. 보존은 역사적 중요도, 핵은 인과적 중요도, 별도 파일은 서술 배율이다.

승격한 문서의 제목은 파일명이 아니라 **책임이 무엇이 되어갔는가**를 말한다. 커밋 연표를 본문으로 올리지 않는다. 연표는 증거로 내린다.

같은 객체에 정적분석 파일을 추가로 만들지 않는다. 역사서가 현재 구조와 이미 연결되면 문서 증식이다.

Closed 판정: 열린 질문이 있어도, 그것이 이 객체의 역사적 형태를 뒤집지 않으면 조사면은 닫는다.
